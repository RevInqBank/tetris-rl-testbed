## 1. 무엇을 왜 만들었나

### 표면의 요구 세 가지

사용자(서울대 원자력공학, 강화학습 공부 중)가 요청한 것은 셋이었다.

1. 직접 손으로 플레이하는 테트리스
2. 옵션을 켜면 RL 에이전트가 무한히 대신 플레이
3. 여러 전략을 동시에 띄워 비교

### 리드가 복원한 진짜 의도

리드가 사용자의 `RL_공부계획.pdf` 를 읽고 요구 3번의 의미를 다시 세웠다.
그 문서의 축은 **"크리틱이 갱신식의 어디에 들어가는가"** 다.
*(크리틱 = 상태의 가치를 추정해 정책 학습을 돕는 별도 신경망. 이것이 있느냐, 어디에 끼어드느냐로 알고리즘이 갈린다.)*

공부계획은 REINFORCE → +기준선 → A2C → DQN → DDPG/TD3 → SAC 순으로 그 축을 따라간다.
그리고 자기점검 1번이 **"행동공간이 이산인가 연속인가"** 였다.

테트리스는 **이산 행동 + 완전한 모델 보유**다. 그래서

- **DQN 까지는 살아남고**
- **DDPG/TD3 와 SAC 은 탈락한다** (연속 행동공간용이다)
- 대신 **탐색 계열**(AlphaZero 방향)의 문이 열린다

→ 그래서 비교 패널 8개를 **공부계획의 축 그대로** 배치했다.
**이 앱은 게임이 아니라 사용자 공부의 실험대다.** 이것이 이 프로젝트의 성공 기준을 바꿨다.
"테트리스가 돌아간다"가 아니라 **"①~④와 탐색 계열이 같은 문제 위에서 나란히 돌고, 왜 다른지가 화면에서 보인다"** 가 목표가 됐다.

### 8개 패널의 배치

| 패널 | 전략 | 크리틱의 역할 | 공부계획 |
|---|---|---|---|
| 1 | Random | 없음 | 대조군 |
| 2 | Dellacherie 수동 가중치 | 없음 — 사람이 정한 평가함수 | 대조군 |
| 3 | CEM 선형 | 없음 — 진화전략이 가중치를 직접 탐색 | 축 밖 대조군 |
| 4 | REINFORCE | 없음 · 실제 리턴 G_t | ① |
| 5 | REINFORCE + 기준선 | 분산 감소용 기준선 (부트스트랩 아님) | ② |
| 6 | A2C (1-step) | 부트스트랩 표적 r + γ·v(s') | ③ |
| 7 | DQN (afterstate) | Q가 정책 그 자체 (argmax) | ④ |
| 8 | 1-ply 탐색 + 학습된 가치 | 탐색이 정책 개선, 가치는 말단 평가 | 4주차 AlphaZero 절 |

⑤ DDPG·TD3 / ⑥ SAC 은 화면에 **회색으로 남겨두고 "이산 행동공간이라 탈락"이라는 사유를 함께 띄운다.**
빼는 것이 아니라 왜 빠지는지를 보이는 것이 공부에 필요하기 때문이다.

### 표에 나온 이름들

| 낱말 | 뜻 |
|---|---|
| **정책** | 상태를 받아 행동을 내놓는 규칙. 여기서 행동은 "조각을 어디에 어떤 방향으로 놓는가" 하나다 |
| **특징** | 판을 숫자 몇 개로 요약한 것. 이 프로젝트는 8개를 쓴다 (착지 높이, 구멍 수, 높이 합, 울퉁불퉁함 등). 정책은 판 전체가 아니라 이 8개 숫자를 본다 |
| **REINFORCE** | 한 판을 끝까지 두고, 실제로 받은 보상으로 정책을 밀어주는 가장 기본 방식 |
| **+ 기준선** | 위와 같되 보상에서 평균치를 빼서 학습이 덜 출렁이게 한 것 |
| **A2C** | 한 수 앞의 가치 추정으로 표적을 만드는 방식 (부트스트랩) |
| **DQN** | 각 행동의 가치 Q 를 학습하고 가장 높은 것을 고르는 방식. 정책이 따로 없다 |
| **CEM** | Cross-Entropy Method. 좋은 후보들의 평균 쪽으로 분포를 좁혀가는 진화적 탐색. 신경망도 크리틱도 없이 가중치 8개를 직접 찾는다 |
| **Dellacherie** | 사람이 손으로 정한 유명한 테트리스 평가 가중치. 학습을 전혀 하지 않는 대조군이다 |
| **afterstate** | 조각을 놓은 **직후**의 판 상태. 테트리스는 놓은 결과를 정확히 알 수 있어 이 표현이 유리하다 |
| **1-ply 탐색** | 다음 한 수까지 펼쳐보고 고르는 것 |

## 2. 어떻게 진행했나

### 팀 구성

리드(사용자와 대화하는 메인 세션) + 팀원 5명. 전원 opus, 각자 tmux 패널에서 동시에 작업했다.

| 이름 | 소유 | 임무 |
|---|---|---|
| engine | `docs/spec.md`, `engine/*`, `web/engine.js` | 규칙 확정, Python 엔진, JS 미러, 패리티 검증 |
| rl | `rl/*`, `weights/*.json` | 특징 정의, CEM, REINFORCE·+기준선·A2C·DQN, 1-ply 탐색 |
| web | `web/index.html`, `ui.js`, `style.css`, `policies.js`, `arena.js` | PLAY·ARENA·LEARN 세 화면 |
| checker | `tests/*` | 규칙 공격, 새 시드 재평가, 패리티 반증 |
| scribe | `docs/TIMELINE.md`, `docs/REPORT.md` | 기록과 보고 |

### 충돌을 막은 장치 — 파일 소유권, 그리고 그것이 못 막은 것

같은 파일을 둘이 고치면 반드시 깨진다. 그래서 **디렉터리 단위로 소유자를 하나씩 정하고,
남의 파일에서 결함을 발견하면 직접 고치지 말고 소유자에게 보고**하도록 했다.

**이 규칙은 작동했다.** web 이 engine 의 무한회전 버그와 rl 의 JSON 규격 위반을 발견했을 때
둘 다 직접 고치지 않고 리포트했고, 소유자가 고쳤다.

**그런데 충분하지는 않았다.** `web/` 파일이 세 번 되돌려지는 일이 있었고, 원인 규명에 세 라운드가 걸렸다.
소유권 규칙은 위반되지 않았다 — 진범은 **web 자신의 읽고-고치고-쓰기가 자기 Edit 를 덮은 것**이었다.

> **소유권은 "누가 고쳐야 하는가"를 정하지 "누가 고쳤는가"를 남기지 않는다.**

이 팀에는 **파일 변경의 감사 로그가 없었다.** 그래서 engine 은 자기 결백을 증명하려고
8개 파일의 sha256 과 나노초 mtime 을 직접 실측해야 했다(§4 참조).
여러 세션이 같은 작업 트리를 동시에 고치는 구조를 다시 짠다면, **이것이 첫 번째로 추가할 장치다.**

### checker 를 늦게 투입한 것

checker 는 처음부터 띄우지 않고 **공격할 대상이 생긴 뒤에** 투입했다.
첫 임무도 리드가 고른 것이 아니라 **engine 이 스스로 "여기가 위험하다"고 지목한 성능 가드**였다.

## 4. 무엇이 틀렸고 어떻게 잡았나

**이 절이 이 보고서의 핵심이다.**

### 논지

> **이 프로젝트에서 실제로 위험했던 것은 틀린 코드가 아니라 "틀렸는데 통과하는 검증"이었다.**

결함은 열한 건이었다. **열한 건 모두 기존 자동 검증을 정상적으로 통과하고 있었다.**
버그를 못 찾은 것이 아니라, 그 버그를 찾을 수 없는 자리에서 찾고 있었다.
열 건은 고쳤고, 아홉 번째(CEM 분산 붕괴)만 수정 후 재측정이 남았다.

### 결함과 사각지대

| 결함 | 왜 자동 검증이 **원리적으로** 못 잡았나 |
|---|---|
| **spec 의 lock delay 가 폐기된 값(0프레임)에 머묾** | 에이전트는 lock delay 와 무관하게 동작한다 → 패리티도 규칙 테스트도 통과 |
| **`landing_height` 가 브라우저에서 상수 0** | 픽스처는 보드만 주입하고 **엔진 `info` 를 통과하지 않는다.** 특징 *함수*는 맞고 *입력*이 비었던 경우다 |
| **B2B 점수가 문서와 구현이 다름** | **패리티는 Python↔JS 가 서로 같은지만 본다. 둘 다 문서와 달라도 통과한다** |
| **무한회전 — lock delay 무력화** | 사람이 프레임 단위로 회전을 계속 넣어야만 재현된다 |
| **`parity.py` 가 JS 붕괴를 "node 없음"으로 보고** | **검증이 실패를 침묵으로 바꿨다** |
| **fastsim 의 스폰 버퍼·게임오버 규칙 상이** | 자기 시뮬레이터 안에서는 일관되므로 **자체 테스트로는 영원히 안 잡힌다** |
| **`PROJECT.md` 의 서빙 방법이 낡아 가중치 11개가 404** | `try/catch` 가 삼켜서 **화면은 정상으로 보이고 AI 패널 6개만 조용히 죽는다.** 문서대로 띄워보지 않으면 알 수 없다 |
| **탐색이 깊이가 다른 두 상태의 가치를 더한다** | **명세가 그렇게 적혀 있었고 구현은 정확히 따랐다.** 패리티도 골든 테스트도 "구현이 문서와 같은가"만 보므로 **문서가 틀리면 통과한다** |
| **CEM 탐색 분포가 3분 만에 붕괴한다** (`sigma` = 0) | **값은 매 세대 정확히 기록되고 있었다.** 아무도 그 열을 안 읽었다. 검증을 늘려도 안 잡힌다 — **기록이 이미 옳기 때문이다** |
| **평가기가 전략을 이름으로 분기해 `search_1ply_sum` 이 조용히 그리디로 돌았다** | 이름과 동작이 갈라져도 **양쪽 다 정상 실행된다.** 숫자가 CEM 과 같아지는 것이 유일한 흔적이었다 |
| **JS 만 계약에 없는 죽음 페널티(`-1e6`)를 적용** | 그 조건이 **11,707수 중 29수에서만 성립**한다. 게임 내내 아무 일도 안 하다가 **맨 끝에서만** 갈라진다 |

*(용어: **lock delay** = 조각이 바닥에 닿은 뒤 고정되기까지의 유예. 이게 있어야 마지막 순간에 밀어넣는 tuck·slide 가 된다.
**B2B** = Back-to-Back, 4줄 삭제를 연달아 냈을 때의 보너스. **패리티** = Python 구현과 JS 구현이 같은 입력에 같은 출력을 내는지 대조하는 것.
**fastsim** = rl 이 학습 속도를 위해 따로 만든 경량 시뮬레이터.)*

#### 일곱 번째 결함은 리드가 낸 것이다 — 자기가 세운 규칙을 자기가 어겼다

리드가 서빙 방식을 프로젝트 루트로 바꾸면서 `tools/serve.sh` 는 고치고 **`PROJECT.md` 는 안 고쳤다.**
checker 가 문서대로 실제로 띄워보고 잡았다 — 가중치 11개가 404 인데 화면은 멀쩡해 보였다.

**그날 리드가 팀에 세운 규칙이 정확히 이것이었다**: *"판정을 내리면 코드와 문서를 같은 작업에서 고친다."*

이 사건을 남기는 이유는 규칙의 요점이 **"리드도 예외가 아니다"** 이기 때문이다.
규칙을 만든 사람이 어겼다는 사실이 빠지면, 이 절의 논지는 "팀원들이 실수했고 리드가 잡았다"로 읽힌다. 그건 사실이 아니다.

#### 여덟 번째 결함은 성질이 다르다 — 명세대로 구현했는데 **명세가 틀렸다**

앞의 일곱은 *"구현이 명세와 다르다"* 거나 *"결정이 전달되지 않았다"* 였다. 이건 아니다.

`searchTwoPly` 의 평가 규칙이 이렇게 돼 있었다.

```
score(p1) = v(1수 후 상태) + max over p2 of v(2수 후 상태)
```

**깊이가 다른 두 상태의 가치를 더한다.** 가중치는 CEM 이 **1스텝 그리디 평가용**으로 학습한 것이라
합산에 의미가 없다 — 중간 노드를 한 번 더 세는 셈이라 **"1수째를 두 배로 중시하는"** 편향된 평가가 된다.
표준은 말단만 평가하는 것이다 (`max over p2 of v`).

**구현은 이 규칙을 정확히 따랐다.** `meta.search` 에 `plies: 2, uses_next_piece: true` 로 규칙이 명시돼 있었고,
코드는 그대로 했다.

> **그래서 패리티도 골든 테스트도 이것을 못 잡는다.**
> 둘 다 *"구현이 문서와 같은가"* 만 본다. **문서가 틀리면 통과한다.**
> §4 의 다른 항목들이 "검증의 사각지대"라면, 이것은 **검증 체계 전체의 사각지대**다.
> 어떤 일관성 검사도 "명세 자체가 옳은가"는 묻지 않는다.

**어떻게 드러났나 — 유일한 단서는 결과의 부자연스러움이었다.**
성능 비교를 하다가 **"탐색을 껐더니 좋아졌다"** 는 말이 안 되는 결과가 나왔다.
탐색은 원리상 더 나쁠 수 없다(같은 가치함수로 한 수 더 보는 것이므로).
그 위화감이 규칙을 다시 읽게 만들었다.

> **교훈: 자동 검증이 원리적으로 못 보는 층이 있고, 거기서는 "결과가 이상하다"가 유일한 신호다.**
> 그 신호를 "학습이 덜 됐나 보다"로 넘기면 영영 안 잡힌다 — `landing_height` 때와 같은 함정이다.

### 각 결함이 낳은 규칙

발견보다 중요한 것은 **같은 유형이 다시 나올 수 없게 만든 것**이다.

| 결함이 드러낸 것 | 그래서 만든 규칙 |
|---|---|
| 대화에서 내린 판정이 문서·소비자에게 안 갔다 (오늘 **다섯 번**) | 판정을 내리면 코드와 spec 을 **같은 작업에서** 고치고 "spec §X 갱신함"을 보고에 명시. **기록 담당에게도 한 줄 통보** |
| 검증 도구가 실패를 침묵으로 바꿨다 | **스킵과 실패를 출력에서 구분**하고 스킵 개수를 요약에 항상 노출 |
| 계약에서 뺀 필드를 읽는 코드가 남았다 | **없어야 할 것이 없는지도 테스트한다** — "엔진은 `landing_height` 를 export 하지 않는다"를 테스트로 고정 |
| 패리티가 문서를 안 본다 | **문서 기준 골든 테스트** — 표를 코드에서 읽지 말고 문서에서 손으로 옮겨 적어 대조 |
| 함수는 맞고 입력이 비었다 | 실제 게임 루프에서 **특징이 상수가 아닌지** 검사 (`liveTest`) |
| 무작위 커버리지가 얇았다 | 커버리지를 운에 맡기지 말 것 — 무작위로 wall kick 이 27회밖에 안 나오면 **전수 조사**로 바꾼다 (실제로 8,084 회전 시도로 전환) |
| 문서가 낡아 실제로 안 돌아갔다 | **문서대로 실제로 띄워본다.** 코드가 도는 것과 문서대로 도는 것은 다른 사실이다 |
| 문장을 조용히 지우면 옛 사본을 든 사람을 못 막는다 | `spec.md` 에 **"폐기 알림" 블록**을 남긴다 — 무엇이 왜 폐기됐는지를 지운 자리에 적는다 |

### 검증 코드도 같은 실수를 한다 — 오늘 네 번

**"고장났다"를 "괜찮다"로 바꿔 보고한 사례가 넷인데, 넷 다 검증하는 쪽에서 나왔다.**

| # | 어디 | 무엇이 침묵했나 |
|---|---|---|
| 1 | `engine/parity.py` | JS 엔진이 **SyntaxError 로 완전히 깨져도** "환경 제약으로 스킵" |
| 2 | 배포 스모크 | `"parity_verified" in meta` 만 봐서 **값이 `null` 인데 통과** (`cem_score.json` 이 그렇게 빠져나갔다) |
| 3 | web 의 U3 재현 테스트 | 통과 조건이 `게임 수 >= 3` 이라 **3판에서 얼어붙은 상태가 그 조건을 만족** |
| 4 | `tests/test_round9_parity.py` | 아래 — **가장 아이러니하다** |

#### ★ 규칙을 집행하는 도구가 그 규칙을 어겼다

```
PASS 0   FAIL 0   SKIP 1
RESULT: the two rounding implementations agree.      ← 거짓
exit 0
```

**카운터는 정직하다** — `SKIP 1 / PASS 0` 이 사실 그대로다.
**그런데 결론 문장이 "일치한다"고 말하고 exit 0 이다.** 아무것도 검증하지 않았는데 통과로 읽힌다.

**그 도구는 checker 가 "스킵을 실패와 구분하라"는 팀 규칙을 집행하려고 만든 것이다.**

> **규칙을 아는 것으로는 부족하고, 그 규칙이 자기 도구에 적용된다는 것을 알아보는 것이 별개의 일이다.**

engine 이 `kind` 판별자로 같은 원칙을 두 번 어긴 것과 정확히 짝이다(바로 아래 절).
**원칙을 세운 사람이 그 원칙의 다음 적용처를 못 알아보는 것**이 오늘 반복해서 나온 형태다.

**없는 값이 답처럼 위장하는 패턴은 프로덕션 코드만의 문제가 아니다.** 검증 코드가 그 실수를 하면 훨씬 오래 안 들킨다.

### 한 파일에서 네 번 — 배포 게이트가 무엇을 보는지 몰랐다

engine 의 배포 스모크 하나에서 **같은 종류의 실패가 네 번** 나왔다.
**게이트를 만드는 것과 게이트가 무엇을 보는지 아는 것은 다른 일이다.**

| # | 무슨 일 | 무엇을 놓쳤나 |
|---|---|---|
| 1 | `weights/` 의 모든 `.json` 에 `parity_verified` 를 요구 → **오탐 4건**(매니페스트·리포트·체크포인트) | 검사 대상을 형식으로 잡았다 |
| 2 | 판별자를 `kind` 로 좁혔더니 **학습 진행 중 산출물**에서 또 FAIL. 앱이 로드하지도 않는 파일이었다 | **"정책 파일인가"와 "배포되는가"는 다른 질문이다** |
| 3 | **"나열됐지만 없는 파일"을 원리적으로 못 잡았다** — `check_weights` 가 **디스크에 존재하는 파일**을 순회한다 | **매니페스트가 앱의 장바구니인데 냉장고만 확인하고 있었다** |
| 4 | 매니페스트가 파싱되지만 이름이 **0개** 나오면 게이트가 통째로 꺼진 채 **all-green 을 보고**한다 | **fail-open 구멍.** 매니페스트 스키마가 이번 세션에 실제로 `weights` → `file` 로 바뀌었으니 가설이 아니다 |

1차를 고치며 engine 이 적은 문장이 원칙이었다.

> **비-배포 사유로 실패하는 배포 게이트는 사람들이 무시하게 되고, 그건 게이트가 없는 것보다 나쁘다.**

**2차가 더 위험했던 이유는 `kind` 라는 그럴듯한 판별자를 썼기 때문에 원칙을 지키고 있다고 믿을 수 있었다는 것이다.**
`kind` 는 형식을 말하고 매니페스트는 배포를 말한다.

**3번이 이 시리즈의 핵심이다.** 게이트 범위를 매니페스트로 좁힌 것(2차 해결)은 옳았는데,
**구현이 여전히 디스크를 순회하고 있었다.** 방향이 반대다 —
매니페스트가 가리키는 없는 파일은 **아예 시야에 들어오지 않는다.**
검사를 추가하자 **즉시 `cem_score_wells.json` 이 잡혔다** — 매니페스트가 나열하는데 없는 파일이었다.

**닫힌 방식이 이 사례의 마무리다.** 파일을 만든 것이 아니라 **매니페스트를 `file: null` 로 바꿨다.**
`random` 처럼 가중치가 없는 전략과 같은 형태다 — **학습 안 된 전략을 목록에 남기되 앱이 가져오려 하지 않게** 한 것이고,
게이트도 그 항목을 건너뛴다. **"없는 것을 나열하지 않는다"의 올바른 처리 형태다.**

**4번은 성공이 실패를 삼키는 형태다.** 파싱은 되는데 결과가 비면 검사할 것이 없어지고,
**검사할 것이 없으면 전부 통과한 것처럼 보인다.** fail-closed 로 고쳤다.

> **리드의 정리: "원칙을 아는 것과 그 원칙이 다음번에 어디에 적용되는지 알아보는 것은 다른 일이다."**
>
> 그리고 네 건이 **모두 같은 파일에서** 나왔다는 것이 이 정리를 뒷받침한다 —
> 문제는 engine 의 부주의가 아니라 **"무엇을 검사 대상으로 삼을 것인가"가 반복해서 어려운 질문**이라는 데 있다.

### 팀 운영의 구조적 한계 — 파일 변경 감사 로그가 없었다

`web/` 파일이 세 번 되돌려져 리드가 engine 에게 "네 생성 스크립트가 범인인가"를 물었다. **답할 방법이 없었다.**

engine 은 `web/` 8개 파일의 sha256 과 나노초 mtime 을 기록하고, 자기 스크립트를 전부 실행한 뒤 재비교하고,
다시 대상 파일을 삭제해 강제 재생성해서 **다른 6개가 무변화임을 실측**해야 했다.

> **내 결백 증명도 사후에 직접 실측해야 했다 — 로그가 있었으면 즉답이었다.**

**rl 도 같은 일을 해야 했다.** `rl/` 전체에서 `web/` 이 등장하는 곳은 **주석 2개와 print 문자열 1개**뿐이고
`symlink`·`os.link`·`shutil.copy/move` 는 **0건**, 쓰기는 전부 `weights/` 아래임을 실측으로 보였다.
rl 이 덧붙인 관찰도 결정적이었다 — **심볼릭 링크는 `web/weights/` → `weights/` 방향이라 `policies.js` 유실을 설명할 수 없다.**

**두 팀원이 각자 결백을 실측으로 증명하고 나서야** 진범이 좁혀졌다 —
외부 프로세스가 아니라 **web 자신의 읽고-고치고-쓰기가 자기 Edit 를 덮은 것**이었다.

**이 팀에는 파일 변경의 감사 로그가 없었고, 그래서 원인 규명에 세 라운드가 걸렸다.**
로그가 있었으면 첫 질문에서 끝났을 일이다.

여러 세션이 같은 작업 트리를 동시에 고치는 구조에서는 **소유권 규칙만으로 부족하다.**
소유권은 "누가 고쳐야 하는가"를 정하지 **"누가 고쳤는가"를 남기지 않는다.**

### ★ 아홉 번째 — **값이 맞게 있었는데 아무도 안 봤다**

앞의 여덟 건은 *"값이 없거나 틀렸다"* 였다. 이건 다르다. **값은 정확히 기록되고 있었다.**

CEM 학습 곡선 파일에 `sigma_norm`(샘플링 분포의 폭)이 **매 세대 찍히고 있었다.**
어느 시점부터 그 값이 **정확히 0** 이 됐고, 그 뒤로 계속 0 이었다.

`sigma` 가 0 이면 샘플링 분포가 **한 점**이다. 64개 후보가 **전부 같은 가중치**이므로
elite 선택이 무의미하고 **학습이 원리적으로 불가능하다.**
그 뒤 elite 값이 오르내리는 것은 개선이 아니라 **매 세대 시드가 바뀌는 평가 노이즈**다.

**리드와 rl 둘 다 `elite_mean_fitness` 열만 보고 "정체 구간"이라고 판단했다.**
정체가 아니라 **탐색이 죽은 것**이었고, 그 차이는 **바로 옆 열에 매 세대 적혀 있었다.**

> **이 유형은 검증을 아무리 늘려도 안 잡힌다. 기록은 이미 옳기 때문이다.**
> 필요한 것은 더 많은 계측이 아니라 **이미 있는 계측을 읽는 것**이다.

**원인은 구현 결함이다.** 표준 CEM 은 **분산 하한**(`sigma = max(sigma, sigma_min)`)이나
**가산 노이즈/재시작**을 둔다. rl 구현에는 **둘 다 없었다.**

> 🔴 **정정, 그리고 그 정정의 정정 — 같은 숫자가 근거 없이 맞았다가, 근거를 갖춰 되살아났다.**
>
> **1차(폐기)**: *"gen 168(약 3분)에 붕괴, 그 뒤 197세대"* — **근거가 없었다.**
> 출처는 리드가 기록자에게 넘긴 곡선 발췌였고 기록자가 검증 없이 실었다(§4 의 리드 행과 같은 계열).
> `weights/curve_cem_*.jsonl` 이 **append-only 인데 실행 구분자(`run_id`)가 없어** 여러 실행이 섞였고,
> **세대 번호가 실행마다 0 부터 다시 시작**하므로 그 `gen 168` 이 어느 실행의 것인지 알 수 없었다.
>
> **2차(폐기)**: checker 가 그 파일을 순차 데이터로 읽어 *"1,398세대 중 617세대(44%) 낭비, gen 649 붕괴"*
> 를 냈다. **같은 함정의 다른 형태다** — 여러 실행을 하나로 뭉쳐 계산했으므로 백분율이 무의미했다.
>
> **3차(확정)**: checker 가 **generation 리셋으로 구간을 분리**했다. 그 파일은 **9개 구간**이고,
> 게다가 병렬 워커가 **interleave 로 append** 해 순차조차 아니었다(`gens 0..641` 다음에 `4..642`).
> **가장 긴 구간(641세대) 하나만 보면:**
>
> ```
> sigma 3.276 → 3.4e-08     붕괴 시작 generation 168     낭비 473/641 = 74%
> 붕괴 후 겉보기 상승 +7.538, 최대가 자기 평균 +2.32 sd  ← 여전히 노이즈 범위
> ```
>
> **1차의 `gen 168` 이 결과적으로 맞았다.** 그러나 **그때 철회한 것은 옳은 처리였다** —
> 근거 없는 참을 기록으로 남기지 않은 것이고, 우연히 맞은 숫자를 지킬 이유는 없다.
> **틀린 것은 숫자였고 방향이 아니었다.** 낭비는 더 크고(44% → **74%**) 붕괴는 더 이르다(649 → **168**).
>
> **교훈(규율로 추가됨)**: **로그 파일을 순차 데이터로 읽기 전에 `generation` 단조성을 확인하라.**
> **행 수와 세대 범위가 안 맞으면 여러 실행이 섞인 것이다.** 병렬 워커가 붙이는 파일은 순차가 아니다.
> checker 가 `curve_cem_lines.jsonl` 이 *"151행인데 generation 0..42"* 인 것을 보고서야 알아챘다.
>
> **부수 정정**: `curve_cem_score_wells10.jsonl` 은 **generation 140 에서 시작한다**(앞 140세대가 파일에 없다).
> 앞선 판의 *"전 139세대 탐색 중"* 류 서술은 **부분 데이터를 전체로 읽은 것**이다.
> **(A) 판정은 유효하다** — 기록된 gen 140~679 구간에서 sigma 최소 **0.06325**, 붕괴 없음.

### 열 번째 — 이름으로 동작을 정하면 이름과 동작이 갈라진다

`rl/evaluate.py` 가 전략을 **이름으로 분기**하고 있었다. 그래서 `search_1ply_sum` 이
**조용히 그리디로 돌면서 CEM 과 같은 숫자를 냈다.** web 도 같은 구조였다.

**하필 이것이 #12 를 재려는 순간에 있었다** — 탐색 규칙 두 개를 비교하려는데
그중 하나가 탐색을 안 하고 있었다.

**고침**: 파일이 선언한 **`meta.search.rule` 로 분기**한다.
검증은 매핑 확인(`search_1ply → leaf`, `search_1ply_sum → sum`, `cem_linear → null`)에서 멈추지 않고
**leaf 와 sum 이 실제로 다른 수를 두는지**까지 봤다.

> **이름으로 동작을 정하면 이름과 동작이 갈라지는 순간 조용히 틀린다.**
> 파일이 자기 동작을 선언하게 하고, 코드는 그 선언을 읽어야 한다.

### 열한 번째 — 조건이 거의 성립하지 않는 코드는 성립하는 순간에만 갈라진다

JS↔Python 정책 경로가 미세하게 갈리는 문제가 오래 열려 있었다. 원인은 이것이었다.

**`scoreAll` 이 게임오버를 유발하는 배치에 `DEATH = -1e6` 을 매기고 있었다.**
**rl 의 탐욕 경로는 그러지 않는다.** web 이 *"당연히 안전하겠지"* 하고 넣은 것이고 **어느 계약에도 없었다.**

**왜 11,700수 동안 안 드러났는지가 요점이다.**

> 게임오버를 유발하는 배치는 **스택이 천장에 닿기 직전에만 존재한다.**
> 시드 900009 는 11,707수 중 그런 수가 **29수뿐이고, 그중 6수가 마지막 8수에 몰려 있다.**

페널티가 게임 내내 아무 일도 안 하다가 **맨 끝 몇 수에서만** 작동한다.
**469/469 체크포인트가 일치하다 마지막 3수에서만 갈린** 이유가 이것이다.

앞의 결함들이 *"값이 없거나 틀렸다"* 였다면 이것은
**"조건이 거의 성립하지 않는 코드가, 성립하는 순간에만 갈라진다"** 이다.
평범한 대조로는 거의 안 잡히고, 잡혀도 **재현이 어려워 우연으로 치부되기 쉽다.**

**결과**: 제거 후 10시드 전부 **줄·조각까지 완전 일치**(이전에는 줄 7/10, 조각 2/10).

#### ★ 그리고 web 은 더 잘 두는 쪽을 버렸다

**페널티가 있는 쪽이 실제로 조금 더 잘 둔다** (+10 · +1 · +1 줄). 그래도 제거했다.

> **보고되는 정책과 다른 정책을 조용히 돌리는 에이전트는,
> 조금 약한 문서화된 정책을 돌리는 에이전트보다 나쁘다.**
> 사용자가 ARENA 에서 보는 플레이가 LEARN 의 표와 같은 정책이어야 한다.

**성능과 정직성이 충돌했을 때 정직성을 택한 사례다.**
그리고 이 보고서의 논지와 정확히 짝이 된다 — §4 의 다른 결함들이 *"틀렸는데 통과했다"* 라면,
**이것은 "틀리지 않았는데도 문서와 다르다는 이유로 버렸다"** 이다.

2수 탐색은 **여전히 DEATH 를 쓴다.** rl 이 `meta.search.death_penalty` 로 **문서화했기 때문이다.**
**같은 상수, 다른 적용 범위** — 그 구분을 주석에 못박았다.
차이를 만든 것은 상수의 좋고 나쁨이 아니라 **계약에 있느냐**였다.

### web 이 스스로 보고한 세 건 — 전부 "결함이 결과처럼 보인" 형태다

web 이 자기 실수 셋을 정리해 넘겼다. **셋 다 같은 모양이다** — 고장이 정상적인 출력으로 위장했다.

| 무엇 | 어떻게 위장했나 |
|---|---|
| **테트리스 비율 단위 착각** — `mean_tetris_rate` 는 비율(0~1)인데 백분율로 읽어 **0.130 을 0% 로** 표시 | 하필 다른 여덟 전략이 **진짜 0** 이라 대조군 역할도 못 했다. **점수 목표 학습의 유일한 성과가 화면에서 사라져 있었다** |
| **DOM 스텁이 통과시킨 것을 실브라우저가 잡았다** — AI 무한 모드가 실제로는 멈춰 있었는데 스텁은 **"167판 재시작 정상"** 으로 보고 | 스텁에 실제 `requestAnimationFrame` 스케줄링이 없었다. **테스트 환경이 없는 기능을 있다고 답했다** |
| **테스트가 멈춘 상태를 PASS 로 판정** — 통과 조건을 `게임 수 >= 3` 으로 썼는데 **3판에서 얼어붙은 상태가 그 조건을 만족한다** | **임계값이 아니라 시간에 따른 증가를 봐야 했다.** 정지는 임계값 검사를 통과한다 |

> **세 번째가 특히 값지다.** "3판 이상 돌았다"는 참인 사실이고 테스트도 정직하게 그것을 검사했다.
> 다만 **그 사실이 "돌고 있다"를 뜻하지 않았다.** §5 에서 말한 *"전부 일치는 범위의 선언"* 과 같은 구조다 —
> 검사가 참을 말하는데 결론이 거짓인 경우다.

### 자기 도구를 걸러서 보면 도구를 오진한다 — checker 의 세 번째 자기 정정

```
bash tests/run_all.sh | grep -E "...FINDINGS IN..."
```

두 가지가 동시에 일어났다.

1. 실제 문자열이 **`FINDINGS OPEN IN`** 이라 **판정 줄이 걸러졌다**
2. **파이프 때문에 exit code 가 `grep` 의 것으로 바뀌었다**

그래서 화면에는 아무 판정도 안 보이고 종료 코드도 이상했다.
checker 는 **"내 러너가 실패를 침묵으로 바꾼다"** 고 결론 낼 뻔했다. **러너는 정상이었다.**

> **규율: 자기 도구를 파이프로 걸러 보고 결론 내리지 마라 — 파이프는 exit code 를 바꾼다.**

**대응이 오늘의 다른 처방과 같은 형태다.** 러너가 파일마다 `VERDICT <name>: CLEAN|FINDINGS` 를 찍고
마지막에 고정 접두사 `SUITE_VERDICT:` 로 총평을 낸다 — **걸러진 화면이 판정을 숨길 수 없게** 만든 것이다.

| 도구 | 무엇을 출력 구조에 실었나 |
|---|---|
| engine 의 벤치 | `QUOTABLE: yes/NO` — **이 숫자를 인용해도 되는가** |
| checker 의 러너 | `SUITE_VERDICT:` — **이 실행이 깨끗한가** |

> **둘 다 판정을 사람의 눈이 아니라 출력 구조에 실었다.**
> 사람이 놓치거나 잘못 필터링해도 판정이 살아남는다.
> §4 에서 반복해 나온 "검증이 침묵한다"에 대한 **가장 이식성 있는 대응 형태**다.

### ★ 코드가 아니라 추론이 틀린 유형 — 오늘 팀 전원이 밟았다

앞의 열한 건은 **코드·문서·계측**의 문제다. 이건 다르다. **전부 사람(에이전트)의 추론이 틀린 것**이고,
형태가 하나로 같다. **팀원 전원과 리드, 그리고 기록자까지 한 번씩 밟았다.**

> **확인된 사실에서 확인되지 않은 연결로 넘어갔다.** — engine 의 자기 진단

| 누가 | 확인된 사실 | 넘어간 결론 | 실제 |
|---|---|---|---|
| engine | checker 의 대조가 통과했다 | "rl 이 `evaluate.py` 로 익스트림을 돌렸을 것" | checker 는 `policies.js` 를 node 로 구동했다. **`evaluate.py` 는 지금도 난이도 인자가 없다** |
| engine | `web/weights` 심볼릭 링크가 세션 중간에 생겼다 | "롤백 범인과 연관됐을 수 있다" | **근거 없는 도약.** web 의 정상 작업이었다 |
| checker | 큐 직접 접근 **0건** | "우회가 없다" | 정적 스캔이 못 보는 경로가 있었다 (§5) |
| 리드 | 파일 mtime 하나 | "되돌린 사람 없음" | 단정할 근거가 아니었다 |
| **scribe** | `policies.js` 에 `\|\| 0` 문자열이 있다 | "결함이 아직 안 고쳐졌다" | **주석 안의 인용문이었다.** 코드는 이미 고쳐져 있었다 |
| **리드** | 두 언어 반올림 규칙이 다르고 **편향 방향이 관측과 일치**한다 | **"그래서 그것이 원인이다"** | 실게임 점수 **42,594개 대조에서 충돌 0건.** 원인은 다른 것이었다 |

**나(scribe)도 여기 들어간다.** 파일 증거를 댄 것은 옳았으나 **주석과 코드를 구분하지 않았다.**
증거를 대는 것과 증거를 읽는 것은 다른 일이다.

**대응 규칙 (engine 이 제안, 팀이 채택)**

> **"확인된 것"과 "그로부터의 추측"을 보고에서 명시적으로 갈라 쓴다.**

이 유형이 위험한 이유는 **틀린 결론이 참인 사실 위에 서 있어서** 검증을 통과한 것처럼 보인다는 것이다.
§5 에서 말한 *"검사가 참을 말하는데 결론이 거짓인 경우"* 와 같은 구조이고,
여기서는 검사 대신 **사람의 추론**이 그 자리를 차지했다.

#### ★ 마지막 행이 가장 위험했다 — 잘못된 원인이 계약이 될 뻔했다

리드의 추론에는 신호가 **셋** 맞물려 있었다. Python `round()` 는 짝수로, JS `Math.round()` 는 +∞ 방향으로
가고 음수에서 반대로 간다 — **규칙이 실제로 다르고**, 예상 빈도가 관측과 **자릿수까지 일치**했고,
**편향 방향도 일치**했다. 근거가 약해서 틀린 것이 아니다.

**그럼 왜 틀렸나 — 증거의 종류를 구분하지 않고 개수로 셌다.**

checker 가 자기 가설이 죽은 뒤에 이 규율을 뽑아냈다.

> **가설을 넘길 때 증거를 등급으로 적어라.**
> **방향성 증거는 강하고, 규모 일치는 우연에 약하다.**
> 셋을 같은 무게로 제시했고, 살아남은 건 방향성 하나였다.

세 신호를 등급으로 다시 보면 이렇다.

| 신호 | 등급 | 실제 |
|---|---|---|
| 규칙이 실제로 다르다 | **약함** — 사실이지만 **원인임을 뜻하지 않는다** | 잠재 위험일 뿐이었다 |
| 예상 빈도가 관측과 **자릿수 일치** | **가장 약함** — 규모 일치는 우연에 약하다 | **우연이었다.** 그런데 이것이 가장 설득력 있어 보였다 |
| **편향 방향** 일치 | **강함** | **유일하게 살아남았다** — 죽음 페널티가 실제로 같은 방향의 편향을 만들었다 |

**셋 중 가장 설득력 있게 느껴진 것이 가장 약한 증거였다.**
"자릿수까지 맞는다"는 정밀해 보이지만, 규모는 여러 원인이 우연히 공유할 수 있다.
반면 **방향은 메커니즘을 가리킨다** — 그래서 그 신호만 진짜 원인까지 이어졌다.

**앞의 추론 오류들은 잘못된 결론에서 멈췄다. 이건 두 걸음 더 갔다.**

1. "정수 키로 통일하라"는 **수정 지시**
2. **"spec 에 계약으로 박아라"** 는 지시

> **그랬으면 다음 사람은 그 문장을 근거로 삼았을 것이고, 틀린 원인 분석이 문서의 권위를 얻었을 것이다.**

**그리고 그 수정 대상이 하필 작동 중인 방어 장치였다.** `argmax_stable`(9자리 반올림 후 argmax)은
§5 에서 확인했듯 **내적 원시값의 34.1% 를 흡수하고 있었다.**
**원인도 아닌 것을 고치려고 재현성의 기준선을 이동시킬 뻔했다** —
발행된 가중치가 **전부 현재 규칙 아래에서 선택·평가됐기 때문**이다.

web 이 실측으로 죽였다: 실게임 점수 **42,594개 대조 → 불일치 0건.** 내적 누산 순서도 반올림 후 **0건.**
**진짜 원인은 web 의 문서에 없던 죽음 페널티였다**(열한 번째 결함).

**철회 후 처리가 오늘의 다른 처방과 같은 형태다.** 규칙 차이 자체는 **실재하므로 없애지 않고**
양쪽 주석에 기록했다 — *"실게임 42,594개에서 충돌 0건 확인, 그러나 보장은 아님.
충돌이 관측되면 여기가 첫 용의자."*
**`KNOWN LIMITATION` 테스트와 같은 처리**다 — 없는 것을 지우는 대신 **있는 것의 범위를 적어둔다.**

### 두 가지 별종 — 위 표에 안 들어가는 실패

앞의 열한 건은 "검증의 사각지대"라는 유형이다. 아래 둘은 성질이 또 다르므로 따로 적는다.

#### (가) 폐기한 숫자에 기대어 내린 결정이 살아남았다

리드가 난이도 모드 실험을 지시하며 목적을 **"1-ply 탐색의 이득이 익스트림에서 증발하는 것을 보이는 것"** 이라고 했다.
근거는 *"탐색이 477 → 1,129줄로 2.4배"* 였다.

**그 수치는 fastsim 결함으로 폐기된 가중치 시절의 것이었다.** 숫자는 폐기됐는데 **그 숫자에 기대어 세운 실험 설계는 폐기되지 않았다.**

> **교훈: 숫자를 폐기하면 그 숫자에 기대어 내린 결정도 함께 재검토해야 한다.**
> 폐기 목록은 값만 지우고 판단은 그대로 남겨두기 쉽다.

#### (나) ★★ 같은 실수를 세 번 했다 — 그리고 세 번째는 실수가 아니었다

엔진 처리량 하나가 **세 번 정정됐다.**

| 세대 | 무엇을 고쳤나 | 무엇을 놓쳤나 | 폐기된 값 |
|---|---|---|---|
| 1차 | 고정 시간 → **고정 개수** (워크로드 고정) | **측정 환경**(부하) | ~~45,307 / 42,938 / 40,099~~ |
| 2차 | **spread ≤ 15%** 가드 추가 | **균일하게 바쁜 기계는 spread 가 좁다** | ~~44,500~~ |
| 3차 | **load ≤ 8** 가드 추가 → `QUOTABLE` 판정 | **가드를 다 통과해도 점 추정은 불가능하다** | ~~46,846~~ |

**매번 원인을 찾아 고쳤고, 매번 남은 변동을 확신으로 착각했다.**

두 가드를 **다 통과한** 측정치 넷이 이렇게 나온다.

```
46,846  (load 6.03, spread 0.8%)
45,170  (load 4.03, spread 5.4%)
45,061  (load 4.23, spread 3.3%)
44,918  (load 3.79, spread 2.1%)
```

**공유 머신이고 부하를 통제할 수 없으므로 세션 간 약 4% 변동이 남는다.**

> **1차와 2차는 측정 방법의 결함이었지만 3차는 결함이 아니다.**
> 4% 변동은 제거할 수 없는 것이었고, **계속 점 추정값을 내놓으려 한 것이 잘못이었다.**

> ⚠️ **최종 답이 범위인 것과, 처음에 범위로 얼버무린 것은 다르다.**
> 1차 실패 직후 한동안 *"약 3만~4만8천, 정책에 따라 변동"* 으로 적었다. 그 범위는 **깨진 측정을 덮는 표기**였다.
> 최종 범위 44,900~46,800 은 **고칠 수 있는 것을 다 고친 뒤 남은 변동**이다.
> **같은 형식이라도 하나는 회피이고 하나는 정직이다.** 무엇을 다 해보고 나서 쓴 범위인지가 그 차이를 만든다.

engine 의 최종 서술:

> 처리량 수치는 세 번 정정됐다. 두 번은 측정 방법의 결함(시간 예산, 부하 미감지)이었고,
> **세 번째는 결함이 아니라 "제거할 수 없는 변동을 점 추정값으로 보고하려 한 것"이었다.**
> **방어 지표를 두 개까지 쌓은 뒤에야 남은 것이 잡음이라는 사실을 받아들였다.**

앞서 인용한 *"단일 값으로 보고한 것 자체가 잘못된 정밀도였다"* 는 **세 번 반복된 뒤에야 실제로 지켜졌다.**

##### 가드 두 개가 서로 다른 실패를 잡는다 — 둘 다 필요하다

```
load  5.02, spread 16.8%  → 측정 중 부하가 변했다      (spread 가드가 잡는다)
load 26.30, spread  1.0%  → 처음부터 끝까지 바빴다      (load 가드가 잡는다)
```

**한쪽만 있으면 다른 쪽 실패 모드에 눈이 먼다.** 2차 실패가 정확히 그것이었다.

##### 구조적 대응 — 숫자는 복사되고 주의 문구는 안 복사된다

주의 문구를 붙여 숫자를 내놓는 것으로는 부족하다. 그래서 **벤치가 스스로 판정을 출력**하게 했다.

```
QUOTABLE: yes (spread <= 15%, load <= 8)
QUOTABLE: NO -- load 26.30 > 8. The machine was busy; this number measures
          contention, not the engine. Re-run when idle and do NOT record this value.
```

**`QUOTABLE: NO` 인 숫자는 보고서에 쓰지 않는다.**
판정을 **사람의 기억이 아니라 출력 자체**에 실은 것이 이 대응의 요점이다.
checker 의 `SUITE_VERDICT:` 도 같은 형태다(§5) — **오늘 나온 대응 중 가장 이식성이 높은 둘이다.**

##### ★★ 그런데 이 정밀도는 어떤 결정도 바꾸지 않았다

**이 숫자가 답하는 질문은 하나다 — "엔진이 학습을 굶기지 않을 만큼 빠른가."**

가장 나쁜 측정치(**38,692**, 부하 중)조차 **목표 20,000 의 1.9배**다.
**모든 측정치가 목표를 2배 안팎으로 넘긴다.** 자릿수를 다투는 것 자체가 의미 없었다.

> **세 번의 정정이 값어치가 있었던 이유는 숫자가 정확해졌기 때문이 아니라
> 측정 방법의 결함을 두 개 찾았기 때문이다.**
> 정작 그 숫자가 지지하는 결론은 **처음부터 바뀌지 않았다.**

**정밀도에 대한 노력과 그 노력이 바꾸는 결정은 별개다.**
이 구분을 안 하면 아무것도 바꾸지 않는 정밀도에 시간을 쏟게 된다 —
그리고 §5 의 n=10 사례는 **정반대**였다. 거기서는 정밀도가 **결론을 뒤집었다.**
**어느 쪽인지를 먼저 묻는 것이 순서다.**

### 특히 값진 세 사건

#### (1) 좋은 숫자를 버린 일 — 그리고 그것을 가능하게 한 것

rl 이 학습 속도를 위해 별도 시뮬레이터 `fastsim` 을 만들었다. CEM 성적이 **새 시드 10게임 평균 19,998.4줄, 전 게임 무사망**으로 나왔다. 목표의 20배다.

엔진과 패리티를 붙이자 결함 두 건이 나왔다.

| | 무엇이 달랐나 | 증거 |
|---|---|---|
| 1 | 엔진 보드는 22행이고 **조각이 숨은 스폰 버퍼에 걸쳐 착지하는 배치도 합법**인데, fastsim 은 가시 20행만 써서 전부 불법 처리했다 | L 조각: 엔진 **25개** vs fastsim **11개** |
| 2 | 엔진의 게임오버는 *"다음 조각이 스폰 위치에 못 놓임"*, fastsim 은 *"합법 배치가 하나도 없음"* — 같지 않다 | 엔진이 끝났다고 한 국면에서 fastsim 은 배치를 **22개 더** 갖고 있었다 |

**두 결함 모두 fastsim 쪽 게임을 더 어렵게 만들었다.** 즉 성적을 부풀린 것이 아니었다.
그런데도 rl 이 19,998.4줄을 버렸다. 이유는 이랬다.

> *"유리한 방향의 오차라도 그건 다른 게임의 결과이고,
> 다른 게임에서 잘한 정책이 이 게임에서도 잘한다는 보장이 없기 때문입니다."*

**그리고 rl 이 이 공을 사양했다.** 자발적으로 의심한 것이 아니라, 리드가 fastsim 을 승인할 때
**"패리티 통과 전 가중치는 최종본이 아니다"** 라는 게이트를 미리 걸어뒀기 때문에 잡혔다는 것이다.

> **여기서 나온 교훈**: 좋은 결과일수록 검증 장치는 결과가 나오기 **전에** 걸려 있어야 한다.
> 나온 뒤에 의심하는 것은 의심할 동기가 없을 때 작동하지 않는다.
> 19,998.4줄은 숫자가 좋았고 전 게임 무사망이었다. 아무도 의심할 이유가 없었다.

#### (2) 300번 검증하고도 못 잡은 결함

web 은 특징 함수를 **랜덤 보드 300개로 Python 과 300/300 교차검증**해뒀었다. 그런데도 결함이 살아 있었다.

`landing_height`(조각이 착지한 높이)를 브라우저가 **항상 0으로 읽고 있었다.**
Dellacherie 가중치에서 절대값이 가장 큰 항(−4.50, 높이 페널티)이 통째로 죽은 것이다.

**함수는 맞았고 입력이 비어 있었다.** 픽스처는 보드만 넣고 엔진 `info` 를 통과하지 않으므로 이 유형을 **원리적으로 못 잡는다.**

가장 나쁜 점은 증상이었다. **결함이 "학습이 덜 됐다"로 위장됐다.** 정책이 높이를 무시하고 두는데,
화면에는 그냥 못 두는 것처럼 보인다.

수정은 값을 채우는 데서 멈추지 않았다. web 이 코드 주석에 남긴 것:

> 이전 판은 `info.landing_height || 0` 이었고, engine 이 그 필드를 제거했을 때 `|| 0` 이 `undefined` 를
> **조용히 삼켰다** — throw 도, NaN 도, 경고도 없었다. (…) **결함이 저조한 성능으로 위장할 수 있어서는
> 안 되므로**, 필수 필드가 사라지면 이제 한 번 소리치고 UI 에서 계속 소리친다.

**수정 효과 (Dellacherie 기준): 739.4줄 — 1,872조각에서 사망 → 1,198.6줄 — 5/5 상한 도달, 안 죽음.**

> **요점: 검증이 통과했다는 사실이 안전을 뜻하지 않는다. 무엇을 통과시켰는지가 안전을 뜻한다.**

#### (3) 지표를 바꿨더니 새 지표가 같은 것을 다시 재고 있었다

줄 수 지표가 포화됐다. CEM·Dellacherie·1-ply 탐색이 **전 게임 무사망**으로 평가 상한에서 끝나 순위를 못 매겼다.
조각 상한을 20만(배치 80만 회)까지 올려도 안 죽었다. 그래서 지표를 **점수**로 바꿨다.

그런데 첫 시도에서 적합도를 "조각당 점수"로 잡자 문제가 생겼다.
`level` (= 1 + 줄수/10) 이 모든 삭제 점수에 곱해지므로 **level 60 의 싱글(6,000점)이 level 1 의 테트리스(800점)를 압도**한다.
즉 새 적합도가 사실상 **"얼마나 오래 살았나"를 다시 재고 있었다.**

결과가 그것을 그대로 보여줬다 — **조각당 1,546점인데 tetris rate 0.1%.** 오래 살며 싱글만 긁는 정책이었다.

`level` 로 나눠서 싱글 100 / 테트리스 800 / B2B 테트리스 1,200 비율이 살아 있게 고쳤다.

> **교훈**: 포화된 지표를 버릴 때, 새 지표가 옛 지표를 다시 재고 있지 않은지 확인해야 한다.

### 팀원이 다른 팀원의 **결론이 아니라 결론의 근거**를 고쳤다

rl 이 epsilon 비교로 바꾼 뒤 *"규칙을 고쳤더니 일치한다"* 로 결론내려 했다.
**web 이 정정했다** — **적용 전후 플레이가 동일하다(10/10 → 10/10).**

> **"고쳐졌다"가 아니라 "이 변경은 원래 아무것도 안 바꿨다"** 이다.
> 진짜 원인은 죽음 페널티였고, epsilon 변경은 **별개로 제거된 잠재 위험**이다.

**결론은 같은데(일치한다) 근거가 다르다.** 그리고 근거가 틀리면
**나중에 누가 "epsilon 을 바꿨더니 해결됐다"를 근거로 삼는다.**

> 오늘 이 팀에서 반복해서 나온 형태다 — **거짓 근거 위의 참 결론은 언제든 무너진다**(§4 (다) 부류).
> 이번에는 그것을 **팀원이 서로에게** 적용했다.

### 남에게 통보한 규칙을 자기 코드에 적용했는지는 따로 확인해야 한다

(A) 실험의 10종 특징 파일을 **rl 자신의 평가기가 통째로 거부했다.**
`features` 배열이 8종과 **정확히 같은지**를 검사하고 있었기 때문이다.

**그 규칙은 리드가 web 에게 경고한 바로 그 지점이다** — *"소비자는 인덱스가 아니라 이름으로 읽어라."*
web 은 그 경고를 받고 고쳐서 **10종 파일이 올 때 깨질 결함을 미리 막았다**(§5).
**정작 그 통보의 발신 쪽에 있던 rl 의 평가기가 같은 규칙을 안 지키고 있었다.**

> **남에게 통보한 규칙을 자기 코드에 적용했는지는 따로 확인해야 한다.**

**오늘 세 번째 같은 형태다.**

| 누가 | 무엇을 알고 있었나 | 어디서 어겼나 |
|---|---|---|
| engine | "비-배포 사유로 실패하는 게이트는 무시당한다" | 같은 파일에서 **네 번** |
| checker | "스킵을 실패와 구분하라" | **그 규칙을 집행하려고 만든 도구**에서 |
| rl | "소비자는 이름으로 읽어라"(web 에게 통보) | **자기 평가기**에서 |

> **원칙을 아는 것과 그 원칙이 자기 코드에 적용된다는 것을 알아보는 것은 별개의 일이다.**
> 셋 다 원칙을 **정확히 알고 있었고**, 셋 다 **자기 쪽에서 어겼다.**

### 두 사람이 각자 밟은 같은 고장 — 문자열 치환의 앵커

| 누가 | 무슨 일 |
|---|---|

> **교훈: 여러 지점을 고칠 때는 Edit 도구를 쓴다 — 고유성을 강제해 주기 때문이다.**

같은 고장을 **두 사람이 독립적으로 밟았다**는 것이 이 항목의 요점이다.

### 불일치의 모양이 원인을 가리킨다 — checker 의 진단 감각

checker 가 하네스 버그를 **보고 전에** 잡았다.

체크포인트 개수가 **152 대 151** 로 하나 달랐다. 그런데 **최종 줄 수는 정확히 일치**했다.

> **"모든 공통 체크포인트가 맞는데 길이만 1 다르다"는 하네스를 먼저 의심할 신호였다.**

파보니 rl 이 **격자 밖에 터미널 레코드를 하나 더 붙이고** 있었다. 정책 문제가 아니었다.

**같은 감각이 오늘 한 번 더 나왔다** — 죽음 페널티를 **편향 방향**으로 좁힌 것.
불일치가 *무작위로* 나는지 *한쪽으로* 쏠리는지, *전 구간*인지 *끝에서만*인지가
**원인의 종류를 가리킨다.**

> **불일치의 크기보다 모양이 정보를 준다.**

### rl 의 방법론 교훈 둘

**(가) 검증이 통과한 것은 결함이 없어서가 아니라 결함이 있는 영역에 도달하지 못해서일 수 있다**

패리티 테스트를 **무작위 배치**로 돌리고 있었다. 무작위는 **23수에 죽어 보드가 낮게 유지되는데,
동점은 보드가 높고 복잡해져야 생긴다.** 그래서 패리티는 계속 PASS 인데
**두 하네스의 숫자는 44% 어긋나 있었다** — 한 시드에서 **1,996줄 대 800줄**, 그리고 **둘 다 계산은 맞았다.**

같은 형태를 두 번 밟았다.

| | 검증 범위 | 실제 갈림이 난 곳 |
|---|---|---|
| 1차 | 무작위 정책 → **얕은 보드만** | 보드가 높아진 국면 |
| 2차 | **3,000수** 검증 | **11,703수** |

> **검증 범위가 실제 사용 범위보다 짧으면 통과해도 안전하지 않다.**

§5 의 *"전부 일치는 범위의 선언"* 과 같은 말이고, 여기서는 그 범위가 **깊이**였다.

**(나) 한 곳을 고치면 그 값을 읽던 곳을 전부 훑어라**

`--minutes` 가 실제 예산이 되도록 `--generations` 기본값을 100,000 으로 올렸더니,
**조각 상한 스케줄이 `gen/generations` 로 계산돼 영원히 첫 칸에 고정**됐다.
탐색 학습 첫 시도가 **14분 내내 상한 100 에서** 돌았고 elite 가 38줄에서 멈췄다.

rl 의 두 번째 사례가 더 조용하다. `eval_summary.json` 이 `--only` 실행에 덮여 8전략이 날아간 사고를
**누적 방식으로** 고쳤는데, 누적하면 **서로 다른 조건의 행이 한 표에 섞인다**는 새 위험이 생겼다.

| 새 위험 | 막았나 |
|---|---|
| 조각 상한 혼재 | **막았다** (경고 출력) |
| **표본 크기 강등** | **안 막았다** |

그래서 전 전략을 n=10 으로 재평가한 **한 번에 ①②③④의 n=200 행 4개가 n=10 으로 덮였다.**

> **표는 멀쩡해 보이고 검정력만 조용히 사라진다.**
> **그리고 그 표가 바로 "순위를 말해도 되는가"를 결정하는 표였다.**

> **한 위험을 막을 때 같은 종류의 다른 위험을 함께 훑지 않으면, 고친 곳 옆에서 같은 사고가 난다.**

checker 의 **"수정이 위험을 옮기면 옮긴 곳에서 다시 때려라"** 와 같은 뿌리다.

### 열한 건을 무엇을 위해 잡았나 — 세 부류

"결함 열한 건"이라는 숫자는 그 자체로는 아무 말도 하지 않는다. **무엇이 달라졌는지로 나누면 셋이다.**

| 부류 | 무엇이 달라졌나 | 사례 |
|---|---|---|
| **(가) 결정을 바꾼 것** | 숫자가 바뀌고 결론이 바뀌었다 | `landing_height`(739→1,198줄) · `sigma` 붕괴(→ (B) 가설 기각) · fastsim 결함(→ 19,998.4줄 폐기) |
| **(나) 방법을 고친 것** | 숫자는 거의 그대로인데 **믿을 수 있게** 됐다 | 벤치 3세대 · n=200 재평가 · 문서 기준 골든 테스트 |
| **(다) 안전하다는 착각을 제거한 것** | **아무것도 안 바뀌었다** | afterstate 누수 · `KNOWN LIMITATION` 테스트 · §8 의 변호 문장 제거 |

**(다)가 가장 세기 어렵다.** 고친 것도 없고 바뀐 숫자도 없어서 **"아무 일도 안 한 것"처럼 보인다.**

afterstate 누수가 그 예다. **동작이 하나도 안 바뀌었고 `1-ply → 0-ply 붕괴` 결론도 그대로다.**
바뀐 것은 **그 결론의 근거**다.

| | |
|---|---|
| 이전 근거 | ~~"정보가 차단됐다"~~ — **거짓** |
| 현재 근거 | "`policies.js` 가 `nextVisibleCount >= 1` 로 올바르게 분기하고 checker 가 2,700수로 확인했다" — **참** |

> **거짓 근거 위의 참 결론은 언제든 무너진다.**

`KNOWN LIMITATION` 테스트는 **기능을 하나도 지키지 않는다.** 그것이 막는 것은
**문서가 실제보다 안전하게 읽히는 것**이다. §8 의 변호 문장 제거는 **코드 한 줄도 안 바꿨다.**

**그런데 이 부류를 소홀히 하면 무슨 일이 나는지 오늘 봤다** —
`stepToward` 프리즈가 **정확히 그 변호 문장 아래에서 자랐다.**
"여긴 괜찮다"고 적어둔 자리는 아무도 다시 안 본다.

### (다) 부류의 교과서적 사례 — `cem_linear` 의 선택법 기록

**패널 3 `cem_linear` 은 이 프로젝트의 헤드라인 정책**인데, 위와 같은 위험(`best_single_candidate` 발행)에
노출돼 있었다. **즉 노이즈 최대값으로 뽑혔을 수 있다.**

**그런데 바꿀 수 없다.** 학습 당시 체크포인트가 rl 의 버그로 사라졌다 —
`--objective lines` 가 탐색 실행과 그리디 실행을 구분하지 않고 **같은 체크포인트 경로를 써서
나중에 돌린 탐색 학습이 덮어썼다.** 경로는 분리했지만 **잃은 분포 평균은 복원 불가**다.

**리드 판정: 재학습하지 않는다.** 근거 셋:

1. **checker 의 독립 재평가를 통과했다** — 학습에도 평가에도 안 쓴 새 시드 10판에서
   **평균 1,198.4줄, 사망 0회.** 결과적으로 나쁜 가중치가 아니다
2. 재학습하면 패널 3 헤드라인이 전부 바뀌는데 **더 정확해지지도 않는다** — 선택법이 다를 뿐 품질은 검증됐다
3. **"선택법의 위험"과 "이 파일의 품질"은 다른 문제다**

**대신 `meta.selection_note` 에 전부 적었다.**

> **아무것도 바뀌지 않지만 "이 파일은 노이즈 최대값으로 뽑혔을 수 있다"는 사실이 기록됐다.**

**(다) 부류의 정의 그대로다** — 결정도 안 바꾸고 방법도 안 고쳤는데 **"안전하다는 착각"만 제거했다.**
그리고 이 부류가 왜 필요한지도 같이 보여준다: 나중에 누가 이 헤드라인 숫자를 근거로 무언가를 결정할 때,
**그 숫자에 어떤 불확실성이 붙어 있는지가 파일 안에 있다.**

### engine 의 자기 총평

> **오늘 내 쪽에서 나온 결함 중 절반이 내 검증 코드 자체의 결함이었다** —
> node 오진, `parity_verified: null` 통과, 비-배포 오탐, 냉장고만 확인, fail-open, 벤치 3세대.
> **검증하는 쪽도 같은 방식으로 틀린다.**

이것이 §5 의 논지와 짝이 된다. §5 가 *"전부 일치는 자랑이 아니라 범위의 선언"* 이라면, 여기서는
**검증자의 초록불이 검증자 자신에 대해서는 아무 말도 하지 않는다.**

## 5. 무엇을 근거로 "옳다"고 말하는가

§4 는 **틀린 것을 잡은 기록**이다. 이 절은 그 반대다 — **공격했는데 안 깨진 것들**의 목록이다.

이것이 필요한 이유가 있다. "테스트 180개 통과"는 무엇을 통과했는지 말해주지 않는다.
아래는 checker 가 **깨뜨리려고 세운 가설**과 그 공격 방법이다. 전부 반증에 실패했고, 그 실패가 근거다.

#### 이 절의 논지를 가장 잘 보여주는 사례 — 11번

11번은 **정적 스캔이 통과시켰는데 실제로는 누수가 있는** 경우다.

checker 는 `rl/`·`web/` 전체에서 `state.queue` 직접 접근을 검색해 **0건**을 확인했다. 옳은 검사였다.
그런데 engine 이 뒤에 두 번째 경로를 찾았다 — `apply_placement` 가 돌려주는 다음 상태의 `.current` 에
**숨겨진 조각이 그대로 들어 있다.** `.queue` 를 grep 해서는 **원리적으로** 안 잡힌다.

**정적 스캔의 범위와 동역학 대조의 범위가 다르고, 전자가 통과한 것이 후자의 통과를 뜻하지 않는다.**
이 프로젝트에서 안전을 실제로 보장한 것은 정적 스캔이 아니라 **행동 대조**(익스트림에서 1-ply 가 CEM 과 2,700수 동일)였다.

> 만약 보고서에 "정적 스캔으로 우회가 없음을 확인했다"라고 적었다면,
> 그 문장은 **참인 검사 결과로 거짓인 안전을 주장**하게 된다. 표의 "결과" 열을 그대로 결론으로 옮기면 이런 일이 난다.

#### ★★ 방어 장치가 실제로 무엇을 막고 있었는지가 숫자로 보인 드문 경우

`argmax_stable` — 점수를 **9자리로 반올림한 뒤** argmax 를 취하는 규칙이 계약에 있었다.
"부동소수점 오차 때문에" 넣은 것이고, **넣을 당시에는 그것이 무엇을 막는지 아무도 몰랐다.**

JS↔Python 갈림을 조사하다 그 값이 나왔다.

> **내적 원시값의 34.1% 가 마지막 비트에서 다르다. 9자리 반올림 후에는 0건 다르다.**

**이 규칙이 없었으면 이 프로젝트는 재현 불가능했을 것이다.**
34% 어긋난 값 위에서 argmax 를 돌리면 동점 근처에서 선택이 갈리고,
한 번 갈린 선택은 판 전체를 바꾼다 — rl 이 fastsim 에서 겪은 **"1,996줄 vs 800줄"이 상시가 된다.**

> 방어 장치는 보통 **작동한 증거를 남기지 않는다.** 막았기 때문에 아무 일도 안 일어나고,
> 그래서 "이거 필요한가?" 라는 질문에 답할 근거가 없다.
> **이번에는 34.1% 라는 숫자가 그 답이 됐다.**

#### ★★ 같은 파일을 세 방식으로 읽으면 순위가 전부 다르다

**이 프로젝트에서 가장 압축적인 교훈이다.** 같은 가중치, 같은 평가 파일이다.

```
n=10  줄 수        ④ > ② > ③ > ①
n=10  중앙값       ③ > ② > ① > ④
n=200 독립 재현    ④ > ② > ① > ③      ← 이것만 맞다
```

**세 순위가 전부 "정직하게 계산된" 것이다.** 데이터를 조작하지도, 시드를 고르지도, 유리한 지표를 찾아 헤매지도 않았다.
평균과 중앙값은 둘 다 정당한 통계량이고 계산도 옳다. **그런데 셋 중 둘은 틀렸다.**

> **§5 의 논지("검사가 참을 말하는데 결론이 거짓")를 숫자 하나로 보여주는 자리다.**
> 여기서 거짓을 만든 것은 잘못된 계산이 아니라 **표본 크기**였다.

**그리고 우리가 하마터면 이것을 화면에 띄울 뻔했다.**
파일은 이미 만들어져 있었고 **UI 는 이미 그것을 읽고 있었다.**
`§6` 의 독립 재현이 없었으면 **아무도 몰랐을 것이다** — 숫자가 이상해 보이지도 않았기 때문이다.

그래서 대응은 "더 정확히 계산하자"가 아니라 **표본 크기를 노출하고 작은 n 에는 순위를 매기지 않는 것**이었다(§8).
**화면에는 절이 없다.** 독자가 어느 표를 보고 있는지 문서가 통제할 수 없으므로,
문서에서만 역할을 나누는 것으로는 부족하다.

#### ★ n=12 대조 — 작은 표본의 점추정은 맞을 수 있지만 순위는 못 믿는다

checker 가 전체 실행 전에 12시드로 스모크를 돌렸다. **그 결과를 버리지 않고 대조로 남긴 것이 값지다.**

| | ② − ③ | 95% CI | 인접 간격 | 순위 |
|---|---:|---|---|---|
| **n=12** | +28.5 | **[−18.0, +71.5]** — 0 포함 | **3개 전부 분리 안 됨** | **뒤바뀜** (① > ② > ④ > ③) |
| **n=200** | +29.0 | [+23.0, +40.0] | 3개 전부 분리 | ④ > ② > ① > ③ |

> **점추정은 n=12 에서도 거의 맞았다 (+28.5 대 +29.0). 틀린 것은 순위와 확신이었다.**

보고서에 쓸 정확한 문장은 이것이다 (checker 제안):

> n=10 에서는 순위가 뒤집힐 수 있었고 어떤 인접 쌍도 분리되지 않았다.
> n=200 에서 4개 패널 전부가 분리되고, 독립 재계산이 순위와 헤드라인 간격을 재현한다.

**이 교훈은 오늘 세 번 독립적으로 나왔다.**

1. ②③ 순서가 재평가마다 뒤집혔다
2. n=10 과 n=200 에서 순위가 달랐다
3. 이 n=12 대조

세 번 다 같은 말이다 — **표본이 작으면 평균은 대충 맞지만 순위는 우연이다.**
그리고 이 프로젝트의 결론은 평균이 아니라 **순위**에 걸려 있다.

#### ★ 수정이 위험을 옮겼고, 옮겨간 곳이 코드가 아니었다

반올림 건의 후속이다. 두 쪽 다 반올림을 없애고 **`v > best + 1e-9`** 로 갔다.

**이 수정은 원인이 아니었던 것을 고친 것인데도 값어치가 있었다.**

- half-to-even 대 half-up 갈림은 **발생 자체가 불가능해졌다** — 관측되지 않은 게 아니라 **메커니즘이 없어졌다**
- 최악 누산 격차 **3.55e-15** 가 허용오차 1e-9 안쪽으로 **28만 배** — BLAS 차이가 argmax 를 뒤집을 수 없다

**그런데 새 전제가 붙었다.** checker 가 옮겨간 곳을 짚었다.

> **`v > best + EPS` 는 추이적이지 않다.** 여러 점수가 EPS 안에 몰리면 **승자가 순회 순서에 달린다.**
> 지금은 양쪽이 `legal_placements` 를 spec 의 고정 `(rot, x)` 순서로 순회해서 안전하다.
> **그런데 그 정렬이 이제 패리티 트레이스용이 아니라 tie-break 의 하중을 받는다.**

**옮겨간 곳이 코드가 아니라 spec 문장의 역할이다.**
`(rot, x)` 정렬을 규정한 문장은 **글자 하나 안 바뀌었다.**
바뀐 것은 **그 문장이 무엇을 지탱하는가** 다 — 재현용 편의에서 **정확성의 전제**로.

> 이런 이동은 **diff 에 안 나타난다.** 바뀐 줄이 없기 때문이다.
> 그래서 나중에 누가 "이 정렬은 트레이스 재현용이니 바꿔도 되겠다"고 판단할 수 있다.

engine 이 spec §8 에 **그 사유를 덧붙였다.** 문장을 지키는 것이 아니라 **문장이 왜 필요한지를 지키는 처리**다.

**checker 의 규율 "수정이 위험을 옮기면 옮긴 곳에서 다시 때려라"가 세 번째로 적용된 사례**이고,
이번에는 **옮겨간 대상이 코드가 아니었다는 점**에서 앞의 둘과 다르다.

#### 원인 추정에 반증 조건을 붙이는 습관 — 세 번째 작동

팀 규칙 중 하나가 **"원인을 추정하면 그것을 죽일 조건을 함께 적는다"** 였다.
JS↔Python 갈림 조사에서 web 이 가설 4개를 세우고 **전부 실측으로 죽인 기록**을 남겼다.

| 가설 | 반증 방법 | 결과 |
|---|---|---|
| 9자리 반올림 규칙이 다르다 | 실게임 점수 **42,594개** 대조 | **0건** |
| 내적 누산 순서가 다르다 | 종반 특징벡터 **6,930개** | 원시값 34.1% 다르나 **반올림 후 0건** |

> web 의 서술: **"checker 가 반증 조건을 먼저 적어준 덕에 가설에 애착 없이 빨리 죽일 수 있었다."**

**그리고 신호 3(편향 방향)은 맞았다 — 방향이 맞고 메커니즘만 달랐다.**
가설은 틀렸는데 **그 가설이 가리킨 방향이 답으로 데려갔다.**

**이 규칙이 오늘 세 번 작동했다.**

| # | 어디서 | 형태 |
|---|---|---|
| 1 | fastsim 패리티 게이트 | **성공** — 게이트가 미리 걸려 있어서 19,998.4줄을 회수했다 |
| 2 | 탐색 규칙 재측정 | **실패를 명확히** — 해석을 미리 정해 결과를 보고 기준을 고르지 않았다 |
| 3 | JS↔Python 갈림 | **가설은 틀렸지만 방법론이 답을 찾게 했다** |

세 형태가 다 다르다. 그런데 **셋 다 "결과를 보기 전에 판정 기준을 적어둔다"** 는 같은 규칙에서 나왔다.

#### ★★ checker 가 자기가 인정한 구멍을 메웠다

checker 가 먼저 이렇게 인정했다.

> **내 엔진 패리티가 146,554 레코드 일치를 보고하는데 정책 버그를 원리적으로 못 잡는다.**
> 두 엔진은 **배치가 무엇을 하는지**에 완전히 동의한다.
> 대조되지 않던 것은 **어느 배치를 고르는가**다.

**이것이 §4 열한 번째 결함(죽음 페널티)이 그렇게 오래 살아남은 이유다.**
엔진 패리티는 정책 위층을 보지 않는다 — 아무리 레코드를 늘려도 그 층에 도달하지 않는다.

**그리고 `tests/test_policy_layer_parity.py` 를 만들어 메웠다.**
**720 체크포인트 + 최종 `board_hash` 전부 일치** — 즉 web 의 `DEATH` 페널티 제거가
실제로 갈림을 없앴다는 것을 **checker 가 독립으로 확인**한 것이다.

설계에 두 가지가 들어갔다.

- **기준 파일이 선언한 `tie_rule` 을 양쪽 구현이 실제로 쓰는지 먼저 단정한다** —
  *"안 그러면 움직이는 표적과 비교하는 것이 된다."*
- **덮지 못하는 것을 테스트가 스스로 말한다** — 25수 간격이라 **구간 안에서 갈렸다 되돌아오는 경우는 안 보이고**,
  한 정책·시드 3개만 본다.

> 오늘 세운 **"각 검사가 무엇을 증명하지 못하는지도 적는다"** 가 **신규 테스트에서 처음부터 적용됐다.**
> 나중에 붙인 주석이 아니라 **설계에 들어간 것**이다.

#### ★★ 테스트가 코드가 아니라 **문서를 지키기 시작했다**

`"탐색이 그리디에 진다"` 와 `"Dellacherie > CEM"` 은 **실패가 아니라 관측**이다.
그런데 테스트가 그것을 **결함으로 보고**하고 있었다. 그대로 두면 **영원히 빨간불이고 양치기 소년이 된다.**

checker 가 방향을 뒤집고 **실패 메시지를 이렇게 바꿨다.**

> **"결함이다"가 아니라 —**
> **"채택된 결과가 더 이상 재현되지 않는다. 지금 화면에 그 반대가 적혀 있으니 출시 전에 재검토해야 한다."**

**즉 테스트가 코드가 아니라 문서를 지킨다.**

오늘 이 팀을 괴롭힌 것이 대부분 **문서와 구현의 갈라짐**이었다 —
lock delay, `landing_height`, B2B 점수, 서빙 방법. 전부 사람이 뒤늦게 발견했다.
**이 형태는 그 갈라짐을 자동으로 감시한다.**

`test_difficulty` 도 같은 방식으로 바뀌었다. **"줄 수 포화가 있다"** 는 정책의 참인 성질이라 영원히 안 사라지는데,
그것을 실패로 보고하는 대신 **"UI 가 사용자를 측정 가능한 축에 올려놓는가"** 를 검사한다.

> §5 의 다른 항목이 *"무엇을 근거로 옳다고 말하는가"* 라면, 이것은
> **"옳다고 말한 것이 계속 옳은지 누가 지키는가"** 다.
> 보고서에 적힌 결론은 시간이 지나면 코드와 갈라진다. **그 갈라짐에 알람을 붙인 것**이 이 전환이다.

#### 예상된 스킵을 스킵으로 세지 않는다 — 규칙의 반대편

`curve_a2c.jsonl` 과 `curve_dqn.jsonl` 이 `sigma_norm` 이 없어 **SKIP** 으로 나왔다.
그런데 그건 *"검증 안 됨"* 이 아니다 — **경사 학습에는 탐색 분포가 없어 붕괴할 것이 애초에 없다.**
checker 가 분류를 **`out of scope by shape`** 로 바꿨다.

> **예상된 스킵이 구멍처럼 보이면, 스킵을 안 세는 것보다 나쁘다.**

**이것이 "스킵과 실패를 구분하라"의 반대편이다.**

| | 무엇이 문제였나 |
|---|---|
| 원래 규칙 | **스킵을 숨기는 것** — 안 덮인 것이 통과처럼 보인다 |
| 이번 | **스킵이 아닌 것을 스킵으로 세는 것** — 안 덮을 이유가 있는 것이 구멍처럼 보인다 |

**둘 다 목적이 같고 방향만 반대다 — 출력이 사실을 말하게 하는 것.**
한쪽만 지키면 다른 쪽으로 넘어간다.

#### ★ 일어나지 않은 결함 — 오늘의 교훈이 실제로 다음 사고를 막았다

이 절의 다른 항목은 전부 **"공격했는데 안 깨졌다"** 이다. 이건 다르다. **깨질 예정이던 것이 미리 막혔다.**

rl 이 곧 **특징 10개짜리 파일**을 낸다고 통보했다. 그런데 web 코드는 **특징을 위치로 읽고 있었다** —
그 파일이 도착하는 순간 **조용히 틀린 점수를 내기 시작했을 것이다.**

web 이 미리 고쳤다. 이제 **파일의 `features` 배열이 권위**이고 길이도 가정하지 않는다.

**핵심은 모르는 이름을 만났을 때의 처리다.** 경고가 아니라 **하드 스톱**으로 만들었다.

> **계산할 줄 모르는 특징이 있다. 0 으로 채워 잘못 점수를 내느니 안 도는 게 낫다.**

**이것은 `landing_height` 가 `|| 0` 으로 조용히 0 이 됐던 것의 정확한 반대 처방이다.**
같은 상황(모르는 값을 만남)에서 오늘 오전에는 0 을 채웠고, 오늘 저녁에는 멈춘다.

검증도 양방향으로 했다 — **순서를 뒤집은 8개 파일은 정상 등록**(점수 일치),
**모르는 특징이 든 10개 파일은 등록 거부.**

> 이 프로젝트에서 **교훈이 실제로 다음 사고를 막은 첫 사례**다.
> §4 가 "무엇이 틀렸나"의 기록이라면, 이 항목은 그 기록이 **읽히고 적용됐다**는 증거다.

#### 12번의 논거가 바뀐 경위 — 팀원이 팀원에게서 더 나은 논거를 받았다

engine 이 `difficulty` 를 상태 해시에서 뺀 근거는 원래 **경험적**이었다 — *"보드·조각·점수가 안 변하는 것을 확인했다."*
checker 가 개념적 구분을 줬고 engine 이 그것을 채택했다.

> `hold_enabled` 차이는 상태가 아니라 상태에서 나가는 **간선**이다.
> 해시는 상태 동일성 판정이므로 **간선 집합을 담을 의무가 없다.**

같은 결론인데 근거의 층이 다르다. 경험적 확인은 "지금까지는 안 변했다"이고, 이쪽은 "변할 수 없다"이다.

---

> **읽는 법**: 위 표에서 "전부 일치"는 자랑이 아니라 **범위의 선언**이다.
> 예컨대 9번은 "사람 플레이가 옳다"가 아니라 **"무작위·스크립트·그리디 키열 56,143 스텝에서는 갈라지지 않았다"** 는 뜻이다.
> 무엇을 통과시켰는지가 안전을 뜻한다는 §4 의 요점이 여기에도 적용된다.

## 6. 중심 주장의 독립 재현 — ①②③④ 순위

**이 프로젝트의 중심 주장은 "크리틱이 어디 들어가느냐로 결과가 갈린다"이고, 그 주장이 서는 자리가 ①②③④ 네 패널의 순위다.**
그 순위를 checker 가 **독립적으로 재계산했고 재현됐다.**

### 왜 "재실행"이 아닌가 — 삼중으로 독립이다

같은 하네스를 다시 돌린 것이 아니다. 세 가지가 전부 다르다.

| | rl (원본) | checker (재현) |
|---|---|---|
| **시드** | 학습 1~100,000 / 평가 910,000~910,199 | **660,000~660,199** — 양쪽과 안 겹친다 |
| **순전파** | `rl/nn.py` (numpy) | **`web/policies.js` 를 node 로 구동** — 같은 가중치 파일, 서로 독립된 MLP·특징 스케일링 구현 |
| **통계** | 점추정만 | **짝지은 부트스트랩** — 시드 인덱스를 짝지어 리샘플링(독립 리샘플링하면 짝짓기 정보가 버려진다) |

### 결과 — 순위는 재현됐고, 인접쌍 중 둘이 갈린다

**시드 200개**(`910,000..910,199`, 학습에 안 쓴 것) · 조각 상한 3,000 · 엔진 구동 ·
**중앙값** + **짝지은 부트스트랩** 95% CI (4,000회)

| 패널 | 전략 | 중앙값 줄 | 95% CI |
|---|---|---:|---|
| ① | REINFORCE | 76.5 | [70.0, 88.5] |
| ② | REINFORCE + 기준선 | **90.0** | [84.0, 97.5] |
| ③ | A2C (1-step) | 65.0 | [60.0, 69.5] |
| ④ | DQN (afterstate) | **101.5** | [82.0, 124.0] |

**인접 순위쌍** — CI 가 0 을 안 품어야 "갈렸다"고 말할 수 있다.

| 비교 | 차이 | 95% CI | 판정 |
|---|---:|---|---|
| ② − ① | +13.5 | [+1.0, +23.5] | **★ 갈린다** |
| ① − ③ | +11.5 | [+4.0, +24.0] | **★ 갈린다** |
| ④ − ② | +11.5 | [−11.0, +35.0] | **안 갈린다** |

> ⚠️ **"④ DQN 이 최고다"라고 쓰면 안 된다.**
> 중앙값은 가장 높지만 **②와 통계적으로 구분되지 않는다.**

#### ★ 두 독립 측정이 ④에서만 갈린다 — 그것도 결과다

| 측정 | ④ − ② | 95% CI | 판정 |
|---|---:|---|---|
| rl (자기 시드, numpy) | +11.5 | [−11.0, +35.0] | 안 갈린다 |
| checker (독립 시드, JS 구동) | +72.5 | [+29.0, +94.5] | 갈린다 |

**②−③, ②−①, ①−③ 은 두 측정이 일치한다. ④만 갈린다.**

**이건 모순이 아니라 결과다.**

> **①②③ 의 순서는 두 독립 측정에서 재현된다. ④의 위치만 측정에 따라 달라진다.**
> DQN 은 **heavy-tail 이 가장 심한 정책**이고(평균/중앙값 **1.70**), **CI 폭이 다른 셋보다 두 배 이상 넓다.**
> 즉 **④는 다른 셋과 같은 정밀도로 순위를 매길 수 없다.**

**두 독립 측정이 ④에서만 엇갈린다는 사실 자체가 위 경고의 근거다.**

그리고 이 대비가 §6 의 논지를 강화한다 — **우리가 확신할 수 있는 것과 없는 것이 같은 표 안에서 갈린다.**
①②③은 두 번 재현됐고 ④는 두 번 다르게 나왔다.

> **표를 통째로 믿거나 통째로 의심하는 것 대신, 행마다 다르게 읽어야 한다.**

**독립 재현**: checker 가 **독립 시드**(`660,000..660,199`)와 **독립 구현**(`web/policies.js` 를 node 로)으로
②−③ 를 **+29.0, CI [+23.0, +40.0]** 으로 냈고, rl 의 점추정 **+25.0** 이 그 안에 들어온다.
**짝지은 승수로는 ②가 ③을 146/200 시드에서 이긴다.**

### ★ 그래서 무엇이 증명됐나 — 공부계획 축의 양방향

**갈린 두 쌍이 정확히 사용자 공부계획의 ①→②→③ 구간이다.**

> **기준선을 넣으면 좋아지고(①→②), 거기서 부트스트랩으로 한 걸음 더 가면 나빠진다(②→③).**
> ③은 ②에서 `G_t` 를 `R + γ·v̂(S_{t+1})` 로 바꾼 **딱 한 줄**이고, **그 한 줄이 성능을 깎았다.**

왜 그런지도 데이터가 아니라 원리로 설명된다.

> **부트스트랩은 크리틱이 좋을 때만 이득이다.**
> 기준선은 **분산만 줄이고 편향을 안 넣는다.** 부트스트랩 표적은 **편향을 넣는다** —
> 크리틱이 틀린 만큼 표적이 틀리고, **표적이 틀리면 갱신 방향 자체가 틀린다.**
> 10분 학습으로 얻은 `v̂` 는 그 문턱을 못 넘었다.

**이것이 이 프로젝트가 8개 패널을 나란히 세운 이유에 대한 답이다.**
"크리틱이 갱신식의 어디에 들어가는가"라는 축에서, **들어가는 위치에 따라 좋아지기도 하고 나빠지기도 한다**는 것이
같은 문제·같은 예산에서 숫자로 나왔다.

> ⚠️ **범위**: "A2C 가 나쁜 알고리즘"이 아니라 **"이 문제·이 예산(10분)·이 크리틱 품질에서"** 다.
> ③이 ②에 지는 것은 **"부트스트랩이 이득이 되려면 크리틱이 일정 수준 이상이어야 한다"는 조건을 보여주는 것**이다.

### ★★ 이 결론은 세 번 뒤집혔다 — 셋 다 남긴다

**셋 중 뒤의 것이 앞의 것을 부정하는 게 아니라, 앞의 둘이 틀린 이유가 서로 다르다.**

| 시점 | 주장 | 왜 틀렸나 |
|---|---|---|
| n=10 | "①<②, 이론대로 나왔다" | **근거 부실** — 표본 10개로 순위를 말했다 |
| n=200, **안 짝지은** 부트스트랩 | "갈리지 않는다. 앞 주장을 정정한다" | **검정력을 버렸다** — 짝짓지 않아 시드 난이도 분산이 그대로 남았다 |
| n=200, **짝지은** 부트스트랩 | "갈린다" | 현재. 근거가 가장 단단하다 |

**두 번째가 특히 값지다.** 표본을 20배로 늘렸는데 **결론이 오히려 흐려졌다** —
데이터가 아니라 **통계 방법**이 문제였기 때문이다.
전 전략이 **같은 시드**를 쓰므로 짝짓는 것이 옳고, 짝짓지 않으면 시드마다 다른 난이도가 잡음으로 남는다.

> **같은 데이터에서 통계 방법만 바꿔 결론이 바뀌었다.**

checker 의 n=12 대조가 이것을 더 선명하게 만든다 — **점추정은 +28.5 로 거의 정확했는데
CI 가 [−18.0, +71.5] 로 0 을 품었고 4방향 순위는 통째로 틀렸다.**

> **작은 n 에서 틀리는 것은 점추정이 아니라 순서와 확신이다.**

### 중앙값 채택과 표본 확대는 서로 다른 문제를 풀었다

- **오른쪽 치우침은 그대로다** — mean/median 비율 1.06~1.25. **checker 의 다른 시드에서도 그러므로
  rl 의 시드 선택 탓이 아니라 정책의 성질**이다. 중앙값 채택은 이 문제에 대한 답이었다
- **한 판의 지배력은 사라졌다** — 최대 게임이 전체의 **1~2%** 다. n=10 일 때는 **53~58%** 였다.
  **표본을 늘린 것이 편향 문제를 실제로 해결했다**

### ③ A2C 가 꼴찌라는 서술의 범위

④ > ② > ① > ③ 이므로 **③은 정책경사 셋 중 꼴찌일 뿐 아니라 DQN 에도 크게 진다.**

> ⚠️ **"A2C 가 나쁜 알고리즘"으로 읽으면 안 된다.**
> 범위는 **"이 문제·이 예산(10분)·이 크리틱 품질에서"** 다.
> rl 의 해석: **부트스트랩은 크리틱이 좋을 때만 이득이고, 10분 학습으로 얻은 `v̂` 는 그 문턱을 못 넘었다.**

부트스트랩(③)이 기준선(②)에 지는 것은 **부트스트랩이 나쁘다는 뜻이 아니라
"부트스트랩이 이득이 되려면 크리틱이 일정 수준 이상이어야 한다"는 조건을 보여주는 것**이다.
이것이 사용자 공부계획의 축에서 ②와 ③을 가르는 실제 지점이다.

#### 왜 표본 크기가 섞여 있나 — 게으름이 아니라 판단이다

| 정책군 | n | 이유 |
|---|---|---|
| ①②③④ (죽는 정책) | **200** | 208~295조각에서 죽으므로 **200시드가 싸다.** 그리고 이 넷은 **순위가 결론이므로** 표본이 커야 한다 |
| ②③⑧⑨ (상한 도달 정책) | **10** | 200시드로 늘려도 **같은 숫자가 200번 나온다.** 줄 수로는 애초에 순위가 없으므로 **비용만 들고 정보가 0** 이다 |

상한 도달 정책의 점수 축 구분은 **checker 의 8시드 측정**을 쓴다 — Dellacherie **828,400** > CEM **810,550** (8시드 중 7).

> **`n < 50` 인 행에는 순위를 매기지 않는다.** 공동 표기와 같은 처리다.

**이 표가 이 앱의 메시지다. 크리틱을 쓰는 ④~⑦이 크리틱 없는 ②③⑧에 20배 이상으로 진다.**

> ⚠️ **그 격차는 확실하지만, n=10 행끼리의 순위는 읽지 말 것.**
> **①②③④ 사이의 순위는 §6(n=200, 짝지은 부트스트랩)이 유일한 근거다.**

#### 이 표를 읽는 세 가지 주의

**첫째, 1,998 은 실력이 아니라 천장이다.**
조각 하나는 4칸, 한 줄은 10칸이므로 **조각당 0.4줄이 이론 상한**이다.
조각 상한 5,000 × 0.4 = **2,000 이 이 평가의 천장**이고 ②③⑧이 전부 거기 붙어 있다.
상한을 2만으로 올리면 7,998, 5만이면 19,998, 20만이면 79,998 이 나온다. **준 만큼 나오는 숫자다.**

**둘째, ②③⑧ 사이에 순위를 매기면 안 된다.**
1,998.3 / 1,997.5 / 1,998.2 의 차이는 실력 차가 아니라 **시드별 반올림 잡음**이다.
정확한 표현은 이렇다 — *"10게임 전부 죽지 않고 조각 상한에서 종료. 셋 사이의 순위는 이 숫자로 매길 수 없다."*

**셋째, tetris rate 열이 새 지표다.**
줄 수로는 ②③⑧이 구분되지 않지만 **tetris rate 는 전부 0% 근처**다.
즉 이들은 **4줄을 한 번에 지우지 않고 한 줄씩 꾸준히 지우며 버티는 정책**이다.
패널 9만 13.0% 인데, 그 대가로 죽었다.

> **[해결됨] 앞서 화면과 파일이 어긋났던 것은 단위 착각이었다.**
> `eval_summary.json` 의 `mean_tetris_rate` 는 **비율(0~1)** 인데 web 이 백분율로 읽어 **0.130 을 0% 로** 표시했다.
> 하필 다른 여덟 전략이 **진짜로 0** 이라 대조군 역할도 못 했고, 그래서
> **점수 목표 학습의 유일한 성과가 화면에서 사라져 있었다.** 파일 값 13.0% 가 맞다.

### 사람 손 가중치가 학습을 이기는 축이 있다

점수 축에서 **Dellacherie(사람이 손으로 정한 가중치)가 CEM 을 이긴다** — **50.27 대 48.83**
(checker 8시드에서 7/8). 학습한 쪽이 진 것이다.

**정확한 서술은 "진화탐색이 사람을 개선했다"가 아니다.**

> **목표가 아닌 축에서는 학습이 사람을 못 이긴다.**
> CEM 은 **줄 수**로 학습됐고 **점수는 학습 목표가 아니었다.**

그리고 이것이 `cem_score` 를 만든 이유이며, **목표를 점수로 바꾸자 점수 축 1위(58.32)가 됐다.**

> **같은 학습기가 목표를 따라간다.** 이 대비가 "학습이 무엇을 하는가"를 한 줄로 보여준다 —
> 학습은 잘하게 만드는 것이 아니라 **시킨 것을 잘하게** 만든다.

| 1-ply 탐색 | 158 / 159 / 158 | 158 / 159 / 158 | **155 / 159 / 156** | **익스트림에서만 변함** |

**세 가지가 한꺼번에 증명된다.**

1. **Dellacherie 와 CEM 이 세 모드에서 비트 단위로 동일하다.**
   이 둘은 미리보기를 원래 안 쓰는 정책인데, **안 쓴다는 것이 증명된 적은 없었다.**
   정보를 끊었는데 결과가 한 자리도 안 변한다는 것이 그 증명이다. (engine 이 제안한 검증 방법이다)
2. **익스트림의 1-ply 탐색(155/159/156)이 CEM 선형(155/159/156)과 정확히 일치한다.**
   미리보기가 없으면 1수 탐색은 **0수 탐색**이 되고, 두 전략은 가중치가 같으므로
   **글자 그대로 같은 정책**이 된다. 설계 의도대로 무너진 것이다.
3. **붕괴가 조용하지 않다.** `visibleNext()` 가 익스트림에서 `NextPeekBlocked` 를 던지고
   `collapsedToZeroPly: true` 로 보고한다. 빈 배열을 슬쩍 넘기지 않는다.

**이것이 사용자 공부계획 4주차 "내 문제에 미리 돌려볼 수 있는 모델이 있나?" 의 실증이다.**
모델(다음에 무엇이 오는지)이 있으면 탐색이 성립하고, 끊으면 탐색이 사라진다 — 화면에서 보인다.

#### ⚠️ 정보 차단은 **깊이 상한 없이** 새고 있다 — 결론의 근거를 정확히 써야 한다

위 결과를 **"익스트림에서 미래 정보가 차단됐다"** 로 읽으면 틀린다. 그렇게 쓰면 **반증 가능한 거짓 주장**이 된다.

```python
ext = E.new_game(seed, difficulty=EXTREME)
E.visible_next(ext)          # NextPeekBlocked — 여기는 정상 차단
ns, info = E.apply_placement(ext, p)
ns.current                   # ← 숨겨진 다음 조각이 그대로 나온다
```

`apply_placement` 는 **플레이 가능한** 다음 상태를 돌려줘야 하므로 다음 조각을 스폰할 수밖에 없다.
그리고 그 상태에 또 배치를 적용하면 그다음 조각이 나온다. **연쇄에 상한이 없다.**

```
normal  visible_next(5)        : I  Z  L  S  T
extreme afterstate 연쇄(12회)  : I  Z  L  S  T  O  I  L  S  T  Z  O
                                 └─ 앞 5개가 노멀 미리보기와 정확히 일치 ─┘
```

**익스트림이 노멀보다 더 깊이 샌다.** 12에서 멈춘 것은 루프를 12로 잘랐기 때문이지 한계가 아니다.
연쇄 비용은 배치당 호출 두 번이라 사실상 무료다.

> **이 모드가 실제로 제한하는 것은 "미래를 볼 수 있는가"가 아니라
> "미래를 보려면 afterstate 시뮬레이터를 작성해야 하는가"다. 엔진은 그 이상을 보장하지 않는다.**
> — `docs/spec.md` §14

**결론("1-ply 가 익스트림에서 0-ply 로 붕괴한다")은 유효하다. 근거만 다시 쓴다.**

| 쓰면 안 되는 근거 | 정확한 근거 |
|---|---|
| ~~"정보가 차단됐다"~~ | **`policies.js` 가 `nextVisibleCount >= 1` 로 올바르게 분기하고, checker 의 2,700수 대조가 그것을 확인했다** |
| ~~"정적 스캔으로 우회가 없음을 확인"~~ | **정적 스캔은 이 경로를 통과시킨다** (`.queue` 를 grep 해도 안 잡힌다) |

즉 **"막았다"가 아니라 "안 썼다는 것을 행동으로 확인했다"** 이다.
UI 에도 이 한계를 명시하기로 판정했다 — **숨기지 않는 쪽이 교육적으로 낫다.**

##### 한계를 고정하는 테스트가 한계를 과소평가하고 있었다

engine 이 `parity.py` 에 넣은 `KNOWN LIMITATION` 테스트는 **"누수가 존재함"을 주장하는 테스트**였다.
누가 "고치려다" 에이전트 계약을 깨는 것과, 가드가 완전하다고 오해하는 것을 **둘 다** 막으려는 것이었다.

**그런데 그 테스트가 깊이 1 만 확인하고 있었다.** 즉 **축소된 서술을 고정하고 있었다.**
지금은 깊이가 줄어들면 실패한다.

> **"있는 한계를 고정하는 테스트"조차 그 한계를 과소평가할 수 있다.**
> 무엇을 고정하는지가 무엇을 검사하는지만큼 중요하다.

성적표만 보면 "조금 나아지다 말았다"로 읽힌다. **가중치를 열어보면 다른 그림이 나온다.**

**아무도 "우물을 파라"고 가르치지 않았다.** 적합도 함수를 점수로 바꿨을 뿐인데 진화 탐색이 그 전략을 찾아냈다.

독립 증거가 셋 더 있다.

1. **테트리스 비율** — 다른 여덟 전략이 0~0.1% 인데 `cem_score` 만 **13.0%** 다. 실제로 4줄을 지우고 있다
2. **화면** — ARENA 의 점수 패널 보드가 눈에 띄게 **울퉁불퉁하다.** 다른 패널은 평평하다. 숫자와 그림이 같은 말을 한다
3. **줄 수는 오히려 낮다** — 다른 CEM 은 상한까지 안 죽는데 `cem_score` 는 **6/10 만 완주**한다.
   **줄 수를 희생해 점수를 얻는 맞교환**이 수치로 보인다

**55분판에서는 반전이 하나 더 나왔다** — `aggregate_height` 도 **−0.074 → +0.050** 으로 부호가 뒤집혔다.
**높이를 벌하던 정책이 높이를 보상한다.** 우물을 유지한 채 높이 쌓아 I 를 기다리는 전략의 나머지 절반이다.

> **아무도 "한 열을 비워 두고 높이 쌓아 I 를 기다려라"라고 가르치지 않았다.**
> 적합도 함수만 바꿨는데 그 전략이 가중치 두 개의 부호로 찍혔다.

> ⚠️ **"합격선 미달"과 "성향 전환 성공"은 별개 사실이다.** 위 표는 후자만 증명한다.
> 이 표로 합격선 미달을 반박하지 않는다. **둘 다 참이다.**

> 우물을 열어둔 채 I 조각을 기다리는 것은 **지연 보상**이고, 기다리는 동안 높이가 올라가 죽을 위험을 감수해야 한다.

#### ★ 그리고 학습이 스스로 전략을 썼다

```
max_well_depth     +0.5748   ← 두 번째로 큰 항
well_count         −0.3503
```

**양수 깊이 + 음수 개수 = "깊은 우물을 정확히 하나 유지해라".**

rl 이 `well_count` 의 docstring 에 **의도로** 적어둔 문장이 있다 — *"테트리스 전략은 이 값이 정확히 1이길 원한다."*
**학습이 그 문장을 부호로 찾아냈다. 아무도 지정하지 않았다.**

`cumulative_wells` 페널티는 8종 대비 거의 사라졌고(−0.048), `aggregate_height` 는 양수(+0.036)다 —
**높이 쌓아 우물을 유지한다**는 뜻이다.

#### 점수만 오른 게 아니라 생존도 같이 올랐다

8종은 10판 전부 죽었는데(평균 716조각) 10종은 **6판이 상한까지 갔다**(평균 2,228조각).

> **8종에서는 "터뜨리기"와 "오래 살기"가 상충했는데, 우물을 관리할 수단이 생기니 둘이 같이 됐다.**

이것이 §4 의 "지표를 바꿨더니 새 지표가 같은 것을 다시 재고 있었다"와 짝이 되는 결과다 —
거기서는 **표현 수단이 없어 두 목표가 싸웠고**, 여기서는 **수단이 생기자 둘이 같은 방향이 됐다.**

#### 이 비교에 교란이 없다는 근거

```
generations_run: 680      collapsed_at_generation: None      selected: distribution_mean
```

- **680세대 전부 실효** — `sigma_min` 이 분포 붕괴를 막았다 (앞선 55분 8종판은 붕괴 구간을 안고 돌았다)
- 두 실행 모두 **같은 예산·같은 `sigma_min`**
- 가중치는 선택 잡음에 강한 **`distribution_mean`** 으로 뽑았다

> **오늘 하나씩 발견해 막은 세 오염원(예산·분포 붕괴·선택 잡음)이 이 마지막 실험에서는 전부 통제됐다.**
> **그것이 이 결과를 믿을 수 있는 이유다.**

#### 그래도 합격선은 미달 — 1/3, 실패 유지

| 조건 | 결과 | 판정 |
|---|---|---|
| 죽지 않는다 (10/10) | **6/10** | **미달** (8종 0/10 에서 개선) |
| tetris 비율 ≥ 30% | **59.2%** | **달성** (목표치 60% 에 0.8%p 차이) |
| 조각당 점수 `cem_linear` 대비 2배 | **1.68×** | **미달** (8종은 1.27×) |

**기준은 학습 전에 고정했고 결과를 보고 바꾸지 않았다.**
세 지표 전부 개선됐고 둘이 문턱에 근접했지만 **실패는 실패로 기록한다.**

#### 세 단계로 좁혀진 기록

| # | 조건 | tetris | 그때의 판단 |
|---|---|---|---|
| 1 | 15분, 8종 | 13.4% | "방향은 맞는데 약하다" |
| 2 | 55분, 8종 | 38.9% | "(B) 예산이 변수였다" — (B) 기각을 철회한 지점 |
| 3 | **55분, 10종** | **59.2%** | **"(A) 표현력이 진짜 병목이었다"** |

> **최종 판정은 여전히 실패다.** 세 번 개선했는데도 미리 박아둔 세 조건 중 하나만 넘었다.
> **"개선됐다"와 "합격했다"는 다르고, 그 둘을 섞지 않는 것이 이 기록의 요점이다.**

#### 그래서 공부계획의 축은 어떻게 닫히는가

**(A)가 답이었으므로 "크레딧 할당 문제"는 이번 실험에서 병목이 아니었다.**
선형 afterstate 평가로도 **표현할 수단만 주면** 지연 보상 전략(우물 파고 I 기다리기)을 찾아냈다.

> **부트스트랩 크리틱이 필요한 이유를 이 실험이 증명하지는 못했다.**
> 증명된 것은 그 앞 단계다 — **표현할 수 없으면 학습은 시작도 못 한다.**
> 크리틱의 값어치는 §6 의 ①→②→③ 비교가 따로 답한다.

### 9-2. 탐색 (작업 #12) — **완결. 설명을 하나씩 제거하고도 남았다**

**이 결론은 "측정했더니 그랬다"가 아니라 "설명을 하나씩 제거하고도 남았다"이다.**

| 단계 | 가설 | 개입 | 결과 |
|---|---|---|---|
| ① | **합산 규칙이 원인인가** — 깊이가 다른 두 상태의 가치를 더하고 있었다 | 말단 평가로 수정 | **아님.** 고쳐도 같다 |
| ② | **가중치가 그리디용이라 불리한가** — 1스텝 평가용으로 학습됐다 | **탐색을 붙인 채로 CEM 재학습** | **아님.** 재학습해도 같다 |
| ③ | 남은 것 | — | **이 특징 8개로는 한 수 앞을 보는 것이 이득이 되지 않는다** |

**레벨보정 점수/조각 (중앙값)**

| | 값 |
|---|---:|
| CEM 선형 (탐색 없음) | **48.95** ← 여전히 최고 |
| **탐색까지 넣고 학습한 CEM** | 46.88 |
| 1수 탐색 (그리디 가중치) | 46.75 |

**재학습으로 얻은 것이 0.13 이다.**

> web 의 정리: **교란 요인을 제거했는데 결과가 같다** —
> 가설을 세우고, 그 가설이 예측한 개입을 하고, **그래도 안 바뀌는 것을 확인했다.**

**②를 실제로 해봤다는 것이 이 절의 값어치다.** "가중치가 그리디용이라서"는 가장 그럴듯한 변명이었고,
그것을 제거하고도 결과가 같아야 ③으로 갈 수 있다.

#### 그래서 남는 결론

> **탐색이 정책 개선을 한다는 AlphaZero 의 주장은 가치함수가 그 탐색 깊이에 맞게 학습됐을 때 성립한다.**
> 그리고 그 정렬을 맞추려면 **탐색을 학습 루프 안에** 넣어야 하고, 그 순간 **배치당 25배 비싸진다.**
> 공부계획 4주차의 **"매 결정마다 탐색을 돌릴 계산 여유가 있나"는 추론 시점만의 질문이 아니라
> 학습 시점의 질문**이기도 하다.

#### 남은 미검증 조건 — 예산이 대등하지 않다

탐색 롤아웃이 25배 비싸 조각 상한을 **(100, 200, 400, 800)** 으로 낮춰야 했다 —
그리디의 **(200, 500, 1500, 5000)** 대비.

**정확한 서술은 "원리적으로 무익"이 아니라 "이 예산에서는 값을 못 했다"다.**

#### 🔴 폐기 — "재학습하니 46.7 → 47.3 으로 나아졌다"

**그 0.5 는 학습 효과가 아니라 선택 잡음이었다.**

CEM 은 학습이 끝나면 두 후보 중 하나를 발행한다 — `distribution_mean`(최종 분포의 평균) 또는
`best_single_candidate`(전 세대 최고 적합도). `cem_search` 가 후자로 발행돼 **47.3** 을 냈고,
다른 산출물과 맞춰 전자로 바꾸자 **46.8** 이 됐다.

**왜 그런가**: CEM 은 **세대마다 평가 시드를 새로 뽑는다.** 그래서 "전 세대 최고 적합도"는
**가장 좋은 가중치가 아니라 가장 운 좋은 세대의 가중치**일 수 있다.
특히 분포가 좁아진 뒤에는 후보들이 서로 거의 같아지므로, 그때의 적합도 변동은 학습이 아니라
**시드 노이즈의 봉우리**다. **최댓값을 고르면 그 봉우리를 고르게 된다.**

**checker 가 이 위험을 미리 경고했고, 그 경고가 우리 숫자에서 0.5 로 실측됐다.**

**그리고 정정이 결론을 약화시킨 게 아니라 강화했다.**

| 전 | 후 |
|---|---|
| "교란은 실재했으나(46.7→47.3) 격차는 안 닫혔다" | **"교란을 제거해도 아무것도 나아지지 않았다"** (46.7→46.8) |

### 9-3. 사용자 확인 (작업 #8) — **남은 것은 체감 하나뿐이다**

**"아무도 픽셀을 못 봤다"는 더 이상 사실이 아니다.** playwright/chromium 이 확보되면서 대부분 닫혔다.

| 실브라우저로 검증됨 |
|---|
| 레이아웃 · 색 · 정렬 |
| 키 반응성 (평균 6~7ms) |
| AI 무한 모드 순환 |
| 9패널 프레임 유지 (fps 60) |

그 과정에서 결함 3건이 나왔고 web 이 고쳤다 — 수식 박스 세로 잘림 / 크리틱 설명 문단이 영어 / ARENA 정지 시작.

**남은 것은 하나다: 체감 손맛.**

- **DAS/ARR 감각** — 키를 누르고 있을 때 이동이 손에 붙는지
- **lock delay 500ms 가 실제로 편한지** — 판정 #1 이 지킨 것이 tuck 의 재미였는데, 그 재미는 **사람만 판단할 수 있다**

측정으로는 여기까지다. 496ms/736ms/800ms 라는 숫자가 규칙이 의도대로 도는 것은 증명하지만,
**그 규칙이 좋은 규칙인지는 증명하지 못한다.**

*(사용자 확인 결과를 여기에 채운다.)*
